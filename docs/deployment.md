# Развёртывание на VPS через Docker

Основной способ установки — Docker Compose на Ubuntu 26.04 amd64. Стек содержит PostgreSQL 18, Go API с панелью, Xray, временный Chromium/noVNC и Caddy. На сервере не нужны Go и Node.js: GitHub Actions собирает проверяемый архив и доставляет его по SSH. На текущем VPS первая установка уже выполнена: панель открывается, конфигурация Xray применена, серверный VLESS-тест прошёл, а iPhone подключился через Hiddify по LTE. Для первого запуска нового VPS нужно один раз подготовить ограниченный SSH-приёмник; после этого Docker сам поднимает контейнеры после перезагрузки.

Для текущего VPS используйте IPv4 `162.35.172.6` и домен панели `rb-gateway-3708079.duckdns.org`. Домен должен возвращать этот IPv4. Порт 443 занимает Xray, панель работает на HTTPS-порту 8443, Caddy использует порт 80 для выпуска сертификата. SSH остаётся на порту 22. Убедитесь в панели провайдера, что входящие TCP 22, 80, 443 и 8443 разрешены. Дополнительные порты API, PostgreSQL, браузера и noVNC наружу не публикуются.

## Уже выполненный переход с прежней установки

По решению владельца была выполнена чистая Docker-установка с новым набором устройств, базой и ключами. Установщик сначала проверяет архив, собирает образы и запускает новую БД и API. Перед переключением портов он сохраняет конфигурацию и дамп старой базы в `/var/backups/private-gateway/`, затем останавливает старые службы. Если проверка Docker не проходит, он возвращает старые службы и удаляет незавершённый новый стек. После успеха старые файлы и учётные записи остаются для отката. **Старые профили VLESS с новой установкой не работают.** Для нового устройства нужен новый профиль; обычные последующие Docker-обновления сохраняют существующие устройства и ключи.

В репозитории удалены прежний systemd-установщик и Podman worker. Старый выделенный SSH deploy-key переиспользуется: временный приёмник разрешает только передачу проверенного релиза, затем установщик заменяет его обработчиком обновлений Docker. После каждого коммита в `master` workflow **CI/CD** проверяет код, собирает релиз и только после успеха отправляет его на сервер. При ошибке проверок развёртывания не будет. Если более новый коммит уже попал в `master`, устаревший релиз не развёртывается.

## Повседневная работа с текущим VPS

1. Откройте панель `https://rb-gateway-3708079.duckdns.org:8443/`. После [настройки учётной записи](#учётная-запись-администратора) входите по логину, паролю и коду приложения-аутентификатора. До настройки работает прежний токен; он хранится в `/etc/private-gateway-docker/stack.env` на VPS. Не отправляйте учётные данные в переписку и не вставляйте пароль или код в аргументы команд.
2. После создания или отзыва устройства нажмите в панели «Проверить» и «Применить конфигурацию». Убедитесь, что новая и применённая ревизии совпали. Для нового устройства откройте «Профиль»: скопируйте стандартную VLESS-ссылку или покажите QR-код и импортируйте в [совместимый клиент](clients.md). Проверьте внешний IP на устройстве. QR, URI и конфигурационные файлы содержат секрет доступа.
3. Для обновления проекта достаточно готового коммита в `master`: Actions выполняет `verify`, затем `Deploy Docker to VPS`. ПК и загрузка артефакта на сервер при обычных обновлениях не нужны. Сам по себе зелёный `verify` ещё не означает установленный релиз.
4. Удалённый браузер запускается и останавливается кнопками панели. Basic Auth: имя `browser`, пароль — действующий серверный `GATEWAY_API_TOKEN`, отдельно от пароля и TOTP панели. Сеанс noVNC работает с заметной задержкой; после использования остановите его.

Команды диагностики ниже выполняются в SSH-окне VPS; отдельный блок PowerShell помечен явно. Состояние ошибок и оставшиеся задачи см. в [истории](troubleshooting.md) и [roadmap](roadmap.md).

## Первоначальная настройка SSH-приёмника

Ниже сохранены шаги, которыми был подготовлен **текущий** VPS. Повторно запускать bootstrap или установщик поверх работающего стека не нужно. Для следующих версий достаточно успешного коммита в `master` и зелёного этапа `Deploy Docker to VPS`. При установке на другой сервер используйте его адрес, домен, публичный deploy-ключ и соответствующие GitHub Secrets; буквальное повторение приведённых команд отправит релиз на текущий VPS.

1. Создайте пять GitHub Secrets из раздела ниже. Они нужны только для SSH-доставки, а секреты приложения создаются на VPS.
2. Откройте **Actions → CI/CD** для последнего коммита `master`. После зелёного задания `verify` скачайте маленький артефакт **private-gateway-bootstrap** и распакуйте его на Windows, например в `$HOME\Downloads\private-gateway-bootstrap`. В нём пять файлов: `bootstrap.sh`, `bootstrap-receiver.sh`, `verify-release.py`, `commit.sha`, `SHA256SUMS`. Репозиторий закрытый, поэтому анонимная загрузка с `raw.githubusercontent.com` на VPS возвращает `404`. Большой артефакт **private-gateway-linux-amd64** скачивать не нужно.
3. Скопируйте только эту папку на VPS из PowerShell:

   ```powershell
   scp -r "$HOME\Downloads\private-gateway-bootstrap" "romanburov@162.35.172.6:~/"
   ```

   Подключитесь к VPS под `romanburov`. Проверка checksum должна пройти до запуска скрипта. `SHA` берётся из `commit.sha` того же артефакта, так что он соответствует проверенной сборке:

   ```bash
   cd ~/private-gateway-bootstrap
   sha256sum -c SHA256SUMS
   SHA=$(cat commit.sha)
   test -f "$HOME/private-gateway-linux-amd64/deploy-key.pub"
   sudo bash ./bootstrap.sh \
     --ref "$SHA" \
     --host 162.35.172.6 \
     --domain rb-gateway-3708079.duckdns.org \
     --deploy-key "$HOME/private-gateway-linux-amd64/deploy-key.pub"
   ```

   Запускайте `sudo bash` только если каждый файл получил `OK` и публичный ключ найден. Ожидаемая строка: `VPS is ready to receive the first Docker release from GitHub Actions.` Эта настройка сама по себе ещё не запускает Docker. Она сохраняет старые настройки SSH в `/var/backups/private-gateway/`. Не удаляйте старые файлы и службы до успешной установки и проверки клиента.
4. Вернитесь в **Actions → CI/CD** для текущего коммита: после зелёного `verify` этап `Deploy Docker to VPS` передаст архив, проверит его SHA и установит Docker. Если он уже упал до настройки SSH, нажмите **Re-run failed jobs**. При следующем коммите в `master` то же произойдёт автоматически. Первая установка может длиться несколько минут: Docker загружает образы и собирает браузер. Успех отмечен строкой `First Docker deployment verified: <SHA>`; затем последующие обновления выводят `Docker deployment verified: <SHA>`.
5. [Создайте учётную запись администратора через SSH](#учётная-запись-администратора), затем откройте `https://rb-gateway-3708079.duckdns.org:8443/` и войдите по логину, паролю и шестизначному коду. Проверьте «API подключён», «База данных подключена», «Xray настроен» и равенство применённой и новой ревизий. До создания учётной записи действует прежний вход по токену; обновление Docker само его не отключает.

6. Создайте новое устройство, нажмите «Проверить» и «Применить конфигурацию», откройте «Устройства → Профиль». В совместимом клиенте импортируйте VLESS URI из буфера или отсканируйте QR-код; для sing-box/Mihomo доступны собственные форматы файлов. Порядок импорта приведён в [инструкции](clients.md). `127.0.0.1` в сообщении об импорте на iPhone относится к самому iPhone, не к серверу. Проверьте подключение с мобильного интернета и открытие HTTPS-сайта. Один успешный TCP-тест порта 443 не доказывает, что VLESS работает.
7. Для браузера нажмите «Запустить браузер» и откройте ссылку из панели. Если браузер запросит HTTP Basic Auth, пользователь — `browser`, пароль — **серверный `GATEWAY_API_TOKEN`**, а не новый пароль панели. Это отдельная защита noVNC; [разделение секретов браузера и CLI](roadmap.md) ещё запланировано. После завершения нажмите «Остановить браузер». Данные сессии находятся в tmpfs и стираются при остановке.

## GitHub Secrets для автоматического развёртывания

В GitHub откройте **Settings → Secrets and variables → Actions → New repository secret**. Создайте пять секретов:

| Имя | Значение |
| --- | --- |
| `DEPLOY_HOST` | `162.35.172.6` |
| `DEPLOY_PORT` | `22` |
| `DEPLOY_USER` | `gateway-deploy` |
| `DEPLOY_SSH_KEY` | Полное содержимое закрытого ключа Windows `$HOME\.ssh\private-gateway-actions`. Вставляйте его только в поле GitHub Secret, не в переписку и не в репозиторий. |
| `DEPLOY_KNOWN_HOSTS` | Строка ключа хоста вида `162.35.172.6 ssh-ed25519 ...` из доверенного подключения. На VPS проверьте отпечаток `sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`, затем получите публичный ключ через `sudo cat /etc/ssh/ssh_host_ed25519_key.pub` и добавьте перед ним `162.35.172.6 `. Отпечаток должен совпасть с ранее сохранённым доверенным отпечатком сервера. |

Это только SSH-доступ для доставки релиза. `GATEWAY_API_TOKEN`, ключи REALITY, пароль PostgreSQL и другие секреты приложения остаются в `/etc/private-gateway-docker/stack.env` на VPS. `.env` на вашем ПК GitHub Actions не читает. Закрытый SSH-ключ должен работать без интерактивного ввода пароля в Actions. Настройка секретов и SSH-приёмника выполняется один раз; после неё ваш ПК для развёртывания не нужен. `verify` — CI, то есть проверки и сборка. `Deploy Docker to VPS` — CD, то есть доставка и установка проверенного релиза. Два артефакта имеют разные цели: `private-gateway-bootstrap` нужен один раз для подготовки VPS, `private-gateway-linux-amd64` содержит релиз и передаётся на сервер автоматически.

Для проверки откройте **Actions → CI/CD** после следующего коммита в `master`: сначала завершится `verify`, затем `Deploy Docker to VPS`. Успешный этап выводит `Docker deployment verified: <SHA>`. На VPS можно сравнить `sudo cat /etc/private-gateway-docker/installed.version` с SHA коммита и проверить `sudo docker compose --env-file /etc/private-gateway-docker/stack.env -f /opt/private-gateway-docker/current/docker/compose.yml ps`. Новый релиз сохраняет существующие устройства, базу и ключи Docker. Перед миграцией создаётся дамп PostgreSQL и копия env в `/var/backups/private-gateway/`; при ошибке выполняется откат. Если откат тоже завершился ошибкой, не повторяйте запуск без проверки этого backup и состояния контейнеров.

## Учётная запись администратора

После зелёного `verify` и `Deploy Docker to VPS` с версией, содержащей новую форму входа, выполните **в SSH-терминале на VPS**, где приглашение начинается с `romanburov@vps3708079`:

```bash
sudo python3 /opt/private-gateway-docker/current/docker/admin-credentials.py
```

Команда спросит логин (3–64 латинские буквы, цифры, точка, дефис или подчёркивание; также можно использовать адрес электронной почты длиной до 64 символов) и новый пароль (минимум 14 символов) дважды. Пароль при вводе не отображается. Затем она один раз покажет секрет и `otpauth://`-адрес: добавьте его в приложение-аутентификатор, например Google Authenticator, Microsoft Authenticator или 2FAS, и введите показанный приложением шестизначный код **в том же терминале**. Никому не отправляйте секрет, адрес, пароль или код. Для кодов важно правильное время на телефоне и VPS.

Скрипт не меняет доступ, пока код не подтверждён. После подтверждения он сохраняет закрытую копию старого `stack.env` в `/var/backups/private-gateway/`, перезапускает только API и проверяет через HTTPS вход с новыми данными. При сбое возвращает прежние настройки и перезапускает API; сообщение укажет расположение backup. Дождитесь **следующего** кода в приложении, обновите вкладку панели и войдите. Действующие VLESS-устройства, REALITY-ключи и база не меняются. Чтобы позже изменить логин, пароль или приложение-аутентификатор, повторите ту же команду через SSH с `sudo`; повторный запуск создаёт **новый** TOTP-секрет и завершает прежние сеансы панели.

До успешной настройки панель продолжает принимать прежний токен. После неё публичный API принимает только временный сеанс, выданный за три фактора; сессия живёт не более восьми часов и пропадает при перезапуске API. `GATEWAY_API_TOKEN` остаётся для `gatewayctl` **внутри API-контейнера** и для отдельного пароля noVNC. Его ротация выполняется прежним `rotate-admin-token.py` и не меняет логин, пароль или TOTP.

## Проверка и диагностика

Эти команды не выводят URI устройств:

```bash
sudo docker compose --env-file /etc/private-gateway-docker/stack.env \
  -f /opt/private-gateway-docker/current/docker/compose.yml ps
sudo docker compose --env-file /etc/private-gateway-docker/stack.env \
  -f /opt/private-gateway-docker/current/docker/compose.yml logs --tail=100 api xray browser caddy
curl --noproxy '*' -fsS \
  --resolve rb-gateway-3708079.duckdns.org:8443:127.0.0.1 \
  https://rb-gateway-3708079.duckdns.org:8443/readyz
sudo ss -lntp | grep -E ':(22|80|443|8443)[[:space:]]'
```

Если совместимый клиент показывает тайм-аут, а порт 443 отвечает, проверьте настоящий VLESS-трафик на VPS:

```bash
sudo python3 /opt/private-gateway-docker/current/docker/vpn-smoke.py
```

Проверка берёт один активный профиль через внутренний API, сверяет его с загруженной конфигурацией Xray, запускает временный локальный Xray-клиент и делает HTTPS-запрос через VLESS. URI, UUID и ключи не выводятся; временный конфиг клиента удаляется после проверки. При сбое команда показывает этап: сверка профиля, соединение VLESS, TLS или ответ сайта. `VLESS traffic OK` подтверждает работоспособность профиля и Xray **на сервере**; подключение из сети телефона нужно проверить отдельно.

Если проверка обрывается на `HTTPS handshake through VLESS`, запустите дополнительную изолированную проверку:

```bash
sudo python3 /opt/private-gateway-docker/current/docker/vpn-smoke.py --isolated
```

Она сверяет публичный ключ профиля с закрытым ключом Xray через OpenSSL, затем временно запускает вторую копию Xray на локальном порту с той же конфигурацией и удаляет временные файлы. Работающий контейнер не меняется. Если изолированная проверка проходит, ищите причину в сетевом пути Docker или окружении контейнера. Если она падает, строка `isolated Xray` покажет тип отказа без вывода UUID и ключей.

При прежней ошибке `REALITY rejected: handshake did not complete successfully` временная проверка с `--isolated-target www.cloudflare.com` прошла, в отличие от `www.microsoft.com`. На текущем VPS рабочие target и SNI **уже заменены** на `www.cloudflare.com`, а обычный `vpn-smoke.py` после этого прошёл. Новые Docker-установки также используют Cloudflare по умолчанию.

Только при переносе другой **старой** Docker-установки, где в `stack.env` ещё указан `www.microsoft.com`, одноразовая миграция выполняется командой:

```bash
sudo python3 /opt/private-gateway-docker/current/docker/change-reality-target.py
```

Скрипт сохраняет закрытую копию `stack.env` и Xray-конфигурации в `/var/backups/private-gateway/`, меняет target и SNI, применяет конфигурацию и проверяет VLESS-трафик. На текущем VPS он уже вернул `VLESS traffic OK: TLSv1.3; target www.cloudflare.com; backup ...`; повторять его для обычных обновлений не нужно. При ошибке `repair and rollback failed` проверьте backup и контейнеры до нового запуска.

После любой смены target откройте **Устройства → Профиль** для активного устройства и импортируйте обновлённый URI или QR в совместимый клиент. Старый URI с `sni=www.microsoft.com` не подходит. Для проверки подключения откройте `https://api.ipify.org/`; он показывает только исходящий IP, и на текущем VPS ожидается `162.35.172.6`. Внешняя проверка с iPhone по LTE уже выполнена; Windows с новым профилем пока не проверен.

Если действующий токен панели будет раскрыт, выполните **на VPS**:

```bash
sudo python3 /opt/private-gateway-docker/current/docker/rotate-admin-token.py
```

Команда создаёт новый случайный токен для внутреннего CLI и пароль Basic Auth удалённого браузера, проверяет доступ и откатывает настройки при сбое. После настройки логина/пароля/TOTP она **не меняет их** и не возвращает публичный вход по токену. Когда удалённый браузер остановлен, правильный Basic Auth может вернуть `502` от прокси noVNC; скрипт допускает это только при обязательном `401` для старого пароля. Существующие устройства, база и REALITY-ключи сохраняются. Токен на текущем VPS **уже ротирован** после раскрытия прежнего; без новой причины повторять команду не нужно. Новый токен хранится в `/etc/private-gateway-docker/stack.env`; скрипт **не печатает** его. Если он нужен для входа в noVNC, прочитайте его только в SSH-окне командой `sudo sed -n 's/^GATEWAY_API_TOKEN=//p' /etc/private-gateway-docker/stack.env` и никому не отправляйте. Профиль устройства и QR открывайте только после входа администратора в панель. QR формируется в браузере без внешнего сервиса; он содержит секрет устройства, поэтому закрывайте окно после импорта.

С Windows проверьте DNS, TCP и настоящий HTTPS с проверкой сертификата:

```powershell
Resolve-DnsName rb-gateway-3708079.duckdns.org -Type A
Test-NetConnection rb-gateway-3708079.duckdns.org -Port 443
curl.exe --noproxy "*" --silent --show-error --output NUL `
  --write-out "http=%{http_code} tls=%{ssl_verify_result}`n" `
  https://rb-gateway-3708079.duckdns.org:8443/
```

`http=200 tls=0` подтверждает панель, но не клиентский VLESS-трафик. Если клиент всё ещё не работает, сравните URI с новым профилем, проверьте применённую ревизию, журналы Xray **на сервере**, попытку с другой мобильной сети и время устройства. Не публикуйте URI, UUID доступа, ключи или полные журналы без очистки.

## Хранение, откат и удаление старого стека

Файл `/etc/private-gateway-docker/stack.env` с правами `0600` содержит секреты. PostgreSQL находится в Docker volume `private-gateway_postgres-data`, состояние Xray — в `/var/lib/private-gateway-docker/xray`, сертификаты Caddy — в Docker volume `private-gateway_caddy-data`. Для восстановления нужны согласованные копии базы и env-файла; один дамп базы не позволит расшифровать профили. Делайте внешнюю зашифрованную копию и проверяйте восстановление отдельно. `docker compose down --volumes` удаляет новую базу и сертификаты; не используйте эту команду для обычной остановки. Для перезапуска сервера достаточно `sudo reboot`, контейнеры используют `restart: unless-stopped`.

После **успешной проверки нового клиента, внешней резервной копии и пробного восстановления** можно удалить старые systemd-службы, Podman worker, host PostgreSQL и старые папки релизов. До этого они отключены, но их файлы оставлены как точка возврата. Очистка старой установки остаётся задачей [roadmap](roadmap.md). Не запускайте старые и новые Xray/Caddy одновременно на портах 443/8443.
