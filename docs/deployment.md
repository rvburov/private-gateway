# Установка на сервер и обновления из GitHub

Установщик рассчитан на **свободный Ubuntu 26.04 amd64 с systemd**. Он устанавливает PostgreSQL 18, API, веб-панель, Xray и отдельный rootless Podman worker для браузера. Для первого запуска нужен администратор с `sudo`. Компиляторы Go и Node.js на сервере не нужны: готовую сборку создаёт GitHub Actions.

Первый запуск на конкретном VPS требует проверки. Зелёный CI подтверждает тесты и сборку, но не доступность SSH, портов провайдера или rootless Podman на этом сервере. Установщик проверяет службы и настоящий браузер и завершится с ошибкой, если проверка не прошла.

## 1. Получить проверенную сборку

В GitHub откройте **Actions → CI**, выберите успешный запуск для текущего `master` с событием `push`. Внизу страницы, в **Artifacts**, скачайте `private-gateway-linux-amd64`. GitHub выдаёт ZIP-архив. Артефакты предыдущей версии workflow и запусков pull request не подходят.

В архиве находятся:

- `release.tar.gz` — бинарники API, CLI и Xray, собранная панель и контекст сборки браузера;
- `release.tar.gz.sha256` — контрольная сумма;
- `install/` — установщик, службы и программа обновления.

Сборка привязана к полному SHA коммита. Manifest содержит контрольные суммы всех файлов. Установщик отказывает при повреждении архива, неизвестных исполняемых файлах, ссылках и попытке записи за пределы каталога релиза.

## 2. Создать отдельный ключ для GitHub Actions

Следующие команды выполняются **на своём компьютере**, пример для macOS/Linux:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/private-gateway-actions -C private-gateway-actions -N ''
```

Если файл уже существует, не перезаписывайте его: используйте ранее созданный ключ либо другое имя. Ключ без парольной фразы нужен для неинтерактивного workflow; на сервере его разрешения будут ограничены одной командой обновления.

Файл `private-gateway-actions.pub` — публичная часть для сервера. Файл без `.pub` — приватная часть для GitHub Actions Secrets. Приватную часть не нужно отправлять на сервер, добавлять в Git, переписку или журналы. Раздел личного аккаунта GitHub **SSH and GPG keys** для этого подключения не используется.

## 3. Передать сборку на сервер

В терминале своего компьютера замените `YOUR_SERVER_IP` и `YOUR_SSH_USER` своими значениями:

```bash
gateway_host=YOUR_SERVER_IP
gateway_login=YOUR_SSH_USER
unzip ~/Downloads/private-gateway-linux-amd64.zip -d ~/Downloads/private-gateway-install
cp ~/.ssh/private-gateway-actions.pub ~/Downloads/private-gateway-install/deploy-key.pub
scp -r ~/Downloads/private-gateway-install "$gateway_login@$gateway_host:~/"
ssh "$gateway_login@$gateway_host"
```

Для нестандартного SSH-порта у `scp` используется `-P`, у `ssh` — `-p`. Проверяйте ключ сервера по отпечатку из консоли провайдера или уже доверенного подключения. При повторной загрузке используйте новый каталог, чтобы не смешать старые и новые файлы.

## 4. Выполнить первую установку

Теперь команды выполняются **на сервере**. Укажите публичный адрес этого VPS:

```bash
cd ~/private-gateway-install
sha256sum --check release.tar.gz.sha256
sudo bash install/install.sh \
  --host YOUR_SERVER_IP \
  --archive "$PWD/release.tar.gz" \
  --deploy-key "$PWD/deploy-key.pub"
```

Пароль `sudo` вводится только в терминале. Установщик проверяет Ubuntu, архитектуру, свободные порты и место, доступность выбранного REALITY target по TLS 1.3 с HTTP/2. По умолчанию используются порт Xray `443`, SNI `www.microsoft.com` и target `www.microsoft.com:443`. Их можно задать через `--port`, `--server-name` и `--target`. Выбор target зависит от доступности с сервера и клиента; успешная TLS-проверка не заменяет проверку подключения Hiddify.

Установка создаёт постоянные ключи в `/etc/private-gateway/gateway.env` с правами `root:gateway 0640`, отдельную базу, службы и пользователей. API получает право перезапускать только `private-gateway-xray.service`; универсальный `sudo` API не выдаётся. Только Xray получает право слушать привилегированный порт.

Браузер собирается и запускается пользователем `gateway-browser`. Проверка проходит через HTTP, WebSocket и настоящий VNC framebuffer, после чего тестовый сеанс останавливается. API получает доступ к Unix socket worker, а контейнер не получает ключей шлюза и host mounts.

В конце выводятся публичные параметры подключения и строка `known_hosts`. Административный токен не выводится. Если установка завершилась ошибкой, сохраните её текст. **Не удаляйте базу, каталоги и ключи для повторного запуска.** Установщик намеренно не перезаписывает существующую установку; частично выполненную установку нужно продолжить после диагностики.

Если первая установка остановилась сразу после включения browser worker socket из-за недоступного рабочего каталога служебному пользователю, используйте исправленный `install/install.sh` из нового CI-артефакта. Перед продолжением проверьте причину по выводу и сохраните существующие файлы. Команда с теми же `--host`, `--archive` и `--deploy-key`, но с дополнительным `--resume`, продолжает только этот этап. Режим проверяет уже созданные учётные записи, ключи, релиз и службы; он отказывает при отсутствии ожидаемого состояния или если настройка `gateway-deploy` уже началась. Для других остановок сначала определите точный этап, не запускайте `--resume` наугад.

SSH и firewall установщик не меняет. Разрешите выбранный TCP-порт Xray в панели провайдера и в уже используемом firewall, сохраняя доступ по SSH. Порты `8080`, `6080` и `5432` не публикуются: панель, браузер и база работают на loopback.

## 5. Проверить панель и подключение

В отдельном терминале своего компьютера откройте туннели:

```bash
ssh -N \
  -L 127.0.0.1:8080:127.0.0.1:8080 \
  -L 127.0.0.1:6080:127.0.0.1:6080 \
  YOUR_SSH_USER@YOUR_SERVER_IP
```

На сервере получите **только административный токен**, не печатая весь файл ключей:

```bash
sudo python3 - <<'PY'
from pathlib import Path
for line in Path('/etc/private-gateway/gateway.env').read_text().splitlines():
    if line.startswith('GATEWAY_API_TOKEN='):
        print(line.split('=', 1)[1].strip("'\""))
        break
PY
```

Эта команда показывает секрет в вашем терминале. Вставьте его в панель `http://127.0.0.1:8080`; не отправляйте вывод в переписку или CI. Туннель должен оставаться открытым во время администрирования.

В панели создайте устройство, примените конфигурацию, экспортируйте профиль и импортируйте его в Hiddify. Проверьте соединение, затем отзовите тестовое устройство, снова примените конфигурацию и убедитесь, что повторное подключение отклоняется. Создание или отзыв записи без применения ещё не меняет работающий Xray.

Запустите браузер в панели и откройте `http://127.0.0.1:6080/vnc.html`. Проверьте окно Chromium и открытие HTTPS-страницы. После остановки и нового запуска cookies и история предыдущего сеанса должны отсутствовать. Дополнительные проверки описаны в [browser.md](browser.md) и [privacy-checks.md](privacy-checks.md).

## 6. Настроить GitHub Actions

В репозитории откройте **Settings → Secrets and variables → Actions → Secrets** и создайте:

| Имя | Значение |
| --- | --- |
| `DEPLOY_HOST` | Публичный IP или DNS-имя VPS, без `ssh://` |
| `DEPLOY_PORT` | SSH-порт, обычно `22` |
| `DEPLOY_USER` | `gateway-deploy` |
| `DEPLOY_SSH_KEY` | Полное содержимое локального `~/.ssh/private-gateway-actions`, включая строки BEGIN/END |
| `DEPLOY_KNOWN_HOSTS` | Полная строка публичного ключа сервера из установщика, после проверки отпечатка |

Для `DEPLOY_KNOWN_HOSTS` нужен **полный публичный ключ**, например `YOUR_SERVER_IP ssh-ed25519 AAAA…`, а не только `SHA256:…`. Для нестандартного SSH-порта начало строки имеет вид `[YOUR_SERVER_IP]:PORT`. Отпечаток ED25519-ключа можно сверить через доверенный терминал сервера:

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Workflow не принимает неизвестный ключ сервера автоматически. При переустановке VPS сначала проверьте новый отпечаток через консоль провайдера и только затем обновляйте secret.

Первое обновление запустите вручную: **Actions → Deploy → Run workflow**, ветка `master`. Введите ID успешного запуска CI для текущего `master`: это число в адресе страницы `.../actions/runs/123456789`. Workflow проверяет, что CI прошёл для текущего коммита `master`, и загружает артефакт именно этого запуска.

После успешной проверки создайте в **Settings → Secrets and variables → Actions → Variables** переменную `DEPLOY_ENABLED` со значением `true`. После этого успешный CI для новых изменений `master` запускает развёртывание автоматически. До этого автоматическое развёртывание выключено; ручной запуск остаётся доступным.

Пользователь `gateway-deploy` может передать архив только установленной программе `/usr/local/sbin/private-gateway-deploy`. SSH-ключ не предоставляет интерактивную оболочку, туннели или произвольные команды администратора. В настройках сервера сохраняйте это ограничение.

## Что происходит при обновлении

Обновления выполняются последовательно. Workflow отвергает устаревший коммит, непройденный CI и артефакт другого события или репозитория. На сервер передаётся только архив релиза. Корневые службы, правило polkit и программа обновления не заменяются содержимым этого архива; изменение этих компонентов требует отдельной административной установки.

Обновление проверяет все файлы, подготавливает новый каталог `/opt/private-gateway/releases/SHA` и собирает браузер от имени worker. Затем оно останавливает API, сохраняет резервную копию базы и конфигурации, запускает миграции от имени `gateway`, переключает `current`, запускает API и применяет Xray-конфигурацию. После применения проверяются готовность API и состояние Xray.

Панель недоступна во время миграции; применение конфигурации перезапускает Xray и может прервать активные соединения. Работающий браузер сохраняет текущий контейнер; обновлённый образ используется при следующем сеансе.

Если ошибка произошла до миграции, прежний API можно безопасно вернуть. После начала миграции программа оставляет API остановленным и сообщает путь резервной копии: простой откат бинарника не откатывает схему PostgreSQL. Предыдущая конфигурация Xray восстанавливается, когда это возможно. Ошибка восстановления также сообщается, а workflow остаётся неуспешным.

## Диагностика и резервные копии

Проверки состояния на сервере:

```bash
sudo systemctl status gateway-api private-gateway-xray --no-pager
curl --fail --noproxy '*' http://127.0.0.1:8080/readyz
sudo ss -lntp
```

Для CLI используйте окружение службы, не передавая токен аргументом:

```bash
sudo systemd-run --quiet --wait --pipe --collect \
  --property=User=gateway \
  --property=EnvironmentFile=/etc/private-gateway/gateway.env \
  /opt/private-gateway/current/bin/gatewayctl status
```

Команды `device export` выводят секретный профиль; не запускайте их в Actions. Журналы `journalctl -u gateway-api` и `journalctl -u private-gateway-xray` просматривайте локально и проверяйте перед публикацией.

Резервные копии перед обновлением находятся в `/var/backups/private-gateway`, доступном только root. Это локальные копии для восстановления после неудачного обновления. Они не защищают от потери всего VPS. Регулярно сохраняйте дамп PostgreSQL и необходимые ключи в отдельных защищённых внешних копиях. Установщик не настраивает внешний backup-сервис и не отправляет туда данные.

При ошибке миграции сначала сохраните текущее состояние и изучите причину. Восстановление требует согласованной пары: дамп базы и соответствующие ключи, а также предыдущая версия приложения. Проверьте `pg_restore` на отдельной базе/сервере перед заменой рабочих данных. Не генерируйте новый `GATEWAY_MASTER_KEY` для существующей базы: старые профили перестанут расшифровываться. Не включайте автоматический повтор deployment до устранения причины ошибки.

Каталоги прежних релизов и резервные копии автоматически не удаляются. Контролируйте свободное место; удаляйте старые копии только после проверенного внешнего резервирования. Временный SSH-ключ первоначальной настройки, если он использовался, после завершения удалите отдельно — ключ Actions должен оставаться отдельным.
