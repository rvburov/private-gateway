# История ошибок и диагностика

Здесь записаны существенные ошибки, которые встретились при запуске текущего VPS. Состояние ниже относится к установке Docker на `162.35.172.6` с доменом `rb-gateway-3708079.duckdns.org`. Команды для обычной эксплуатации находятся в [инструкции по развёртыванию](deployment.md), планы — в [roadmap](roadmap.md). Секретные токены, ключи и VLESS URI здесь намеренно не приводятся.

## DNS, домен и порты

| Симптом | Что выяснили | Итог |
| --- | --- | --- |
| `rb-gateway-3708079.mooo.com` отвечал `NXDOMAIN` через 1.1.1.1, 8.8.8.8 и авторитетные `ns1`–`ns4.afraid.org` | Запись FreeDNS не появилась в опубликованной зоне; добавление адреса в код приложения не могло исправить DNS. | Создан `rb-gateway-3708079.duckdns.org`. Публичный DNS вернул `162.35.172.6`. |
| Раньше в адресе панели приходилось указывать `:8443` | Xray занимал внешний порт 443, а Caddy слушал отдельно 8443. | Новая схема ставит HAProxy на 443: по SNI домена панели он направляет HTTPS в Caddy, остальные соединения — в Xray. Старый `:8443` перенаправляет на обычный URL. Работу после выпуска нужно проверить на VPS. Имя с окончанием `.duckdns.org.com` этому домену не принадлежит. |
| TCP 443 отвечал, а клиент VPN показывал тайм-аут | Доступный порт и TLS fallback REALITY подтверждают только сетевой вход, а не успешную авторизацию VLESS. | Для проверки профиля добавлен `docker/vpn-smoke.py`; после исправления target он вернул `VLESS traffic OK: TLSv1.3`. |

## Отзыв устройства и применение конфигурации

После отзыва устройства панель может показывать «Применённая / новая версия: 5 / 6», а при нажатии «Применить конфигурацию» — ошибку связи с API. Пока версии различаются, старый профиль может оставаться в Xray. Возможная причина: владелец открыл панель через тот же VPN, который перезапускается при применении; разрыв HTTP-запроса раньше отменял серверную транзакцию. Теперь после авторизации сервер завершает применение и запись ревизии, даже если браузер потеряет соединение. Проверка на PostgreSQL с принудительным разрывом клиента это воспроизводит; на рабочем VPS результат ещё нужно подтвердить.

Если ошибка появилась на текущем VPS, отключите VPN на устройстве администратора и обновите панель. При повторной ошибке выполните в SSH на VPS `sudo docker exec private-gateway-api-1 /usr/local/bin/gatewayctl config validate`, затем `sudo docker exec private-gateway-api-1 /usr/local/bin/gatewayctl config apply` и проверьте `sudo docker exec private-gateway-api-1 /usr/local/bin/gatewayctl status`. Секреты эти команды не печатают. Считайте отзыв завершённым только при равных `APPLIED REVISION` и `DESIRED REVISION`. Владелец подтвердил `6 / 6` после выпуска `bdb9c22`, но при повторном нажатии «Применить» увидел ошибку связи: прежняя реализация повторно перезапускала Xray даже без изменений. Теперь сервер считает применение актуальной ревизии завершённым без перезапуска, панель отключает ненужную кнопку и скрывает устаревшую ошибку после подтверждения одинаковых версий. Владелец подтвердил неактивную кнопку и отсутствие ошибки после выпуска `33bb494`.

Ранее отозванные устройства продолжали накапливаться в разделе «Устройства»: в интерфейсе было только «Отозвать», а внешний ключ неизменяемого журнала не позволял удалить строку устройства. Теперь после применения отзыва можно удалить устройство с подтверждением. Из таблицы устройств исчезают запись и зашифрованный секрет, а журнал сохраняет UUID и действия без внешнего ключа на удалённую строку. До равенства ревизий удаление запрещено, чтобы старый профиль не остался в работающей конфигурации Xray без записи в базе.

## Переход на Docker и автоматическое развёртывание

При добавлении входа по паролю и TOTP этап `go test -race ./...` в GitHub Actions однажды завершился ошибкой `TestRealXrayTrafficAndRevocation`: запрос через локальные Xray и SOCKS не успел получить HTTP-заголовки за прежние 3 секунды. Тест использует локальные REALITY target и HTTP origin; сообщение не доказывает поломку рабочего VPS или нового входа. Ожидание реального HTTP-трафика увеличено до 10 секунд для нагруженного CI, а проверка отзыва поставлена после успешного запроса с новым ключом, чтобы отсутствие ответа старому ключу нельзя было принять за отзыв при неработающем сервере. Локально после изменения сквозной тест прошёл восемь последовательных запусков под `-race` и полный `scripts/dev.sh test`; итог нового запуска Actions отмечается отдельно.

Позже этап веб-тестов в CI не нашёл кнопку «Показать QR-код». Тест дожидался значения в поле профиля внутри `<dialog>`, но это поле может быть найдено до того, как браузер сделает диалог доступным для поиска по роли. Тест теперь отдельно ждёт доступную кнопку перед нажатием. Это изменение проверки интерфейса; результат нового запуска CI нужно подтвердить отдельно.

Первый запуск `admin-credentials.py` отклонял адрес электронной почты как логин с сообщением `login must contain 3-64 Latin letters...`: проверка терминального скрипта не разрешала `@`. Скрипт прекращал работу до запроса пароля, поэтому учётные данные и серверные настройки не менялись. Теперь можно ввести обычный логин или адрес электронной почты длиной до 64 символов; запуск команды повторяют по [инструкции](deployment.md#учётная-запись-администратора).

Прежний скрипт показывал секрет 2FA и `otpauth://`-адрес в терминале; один секрет попал в переписку и считается раскрытым. Новый вход переносит прежний логин и хеш пароля в PostgreSQL **без этого TOTP-секрета**. При первом входе после обновления браузер показывает новый QR/ключ и принимает подтверждающий код; только он сохраняется в базе зашифрованным. Новый терминальный скрипт задаёт только логин и пароль, сохраняет backup базы/env и не печатает ключ 2FA. Реальную смену на VPS и вход с новым кодом ещё нужно подтвердить отдельно по [чеклисту](roadmap.md#новый-вход-администратора).

Изначально сервис запускался через host systemd и отдельный Podman/browser worker. Сборка Podman требовала `pasta` из пакета `passt`, а её версия не принимала `uid=10001` в `--tmpfs`. Ручной перенос файлов и `--resume-browser` делали установку хрупкой. Вместо этого в проекте теперь один Docker Compose стек: PostgreSQL, API, Xray, браузер и Caddy. Выбрана чистая установка с новыми ключами и устройствами; старые данные сохранены в backup для возможного отката. Новые обновления Docker уже сохраняют текущую базу и ключи.

| Симптом | Причина или предел проверки | Исправление / состояние |
| --- | --- | --- |
| `curl` на `raw.githubusercontent.com/.../bootstrap.sh` вернул `404`, затем `sha256sum` не нашёл файл | Репозиторий закрытый, а raw URL запрашивался анонимно. | GitHub Actions выдаёт маленький `private-gateway-bootstrap` с `SHA256SUMS`; его один раз копируют на VPS. Большой `private-gateway-linux-amd64` Actions передаёт по SSH самостоятельно. |
| `sha256sum -c SHA256SUMS` не находил файл после ручного переноса | Команда и путь к файлу были введены раздельно; в другой попытке смешались старые папки релиза. | Сверять файлы внутри одной распакованной папки; bootstrap и release verifier проверяют контрольные суммы и соответствие коммиту. |
| Actions падал с `DEPLOY_HOST: Set DEPLOY_HOST in repository secrets` | Секреты GitHub для доставки релиза ещё не были заданы. Локальный `.env` на ПК не поступает в Actions. | Настроены пять Secrets: `DEPLOY_HOST`, `DEPLOY_PORT`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`. Секреты приложения создаются и остаются на VPS. |
| Bootstrap ответил `VPS is ready to receive the first Docker release` | Он подготовил только SSH-приёмник, но ещё не установил контейнеры. | После bootstrap требовался зелёный этап `Deploy Docker to VPS`. `Re-run failed jobs` применим, когда изменены только секреты/SSH; новый коммит в `master` запускает CI/CD автоматически. |
| Первый Docker deploy остановился с `range of CPUs is from 0.01 to 1.00` | Браузеру запросили лимит 2 CPU, а у VPS одно ядро. | Лимит браузера уменьшен до 0.75 CPU. Незавершённая установка откатилась. |
| Caddy не стартовал: `exec /usr/bin/caddy: operation not permitted` | Compose сбрасывал все Linux capabilities, а образу Caddy требовалась `NET_BIND_SERVICE`. | Добавлена только эта capability; CI проверяет запуск Caddy с тем же профилем. Открытый порт 80 на ПК не был причиной отказа. |
| После первого зелёного Docker deploy вместо панели показывались ссылки `assets/` и `index.html` | Веб-файлы имели права `0600` владельца root; API с UID 10001 не мог прочитать `index.html`. | Сборка назначает правильного владельца; CI, установщик и обновление проверяют содержимое HTML панели. |

Зелёный `verify` означает успешные тесты и сборку. Рабочий релиз на VPS подтверждается отдельным зелёным `Deploy Docker to VPS` и проверкой самого сервиса. При новой ошибке нужно смотреть конкретный упавший этап; не следует считать всякий красный запуск причиной повторной ручной загрузки артефакта.

## VPN и профиль Hiddify

1. Первоначальный URI импортировался в Hiddify с трудом; сообщение `Connection refused 127.0.0.1` относилось к локальному адресу iPhone при импорте, а не к VPS. В панели добавлена выдача QR-кода профиля. QR и URI являются секретом устройства.
2. После Docker профиль Hiddify показывал тайм-аут, хотя конфигурация Xray была «Актуальна», TCP 443 был доступен, контейнер Xray работал, а прямой HTTPS из него возвращал `200`.
3. Внешний `curl --resolve www.microsoft.com:443:162.35.172.6` после повторной попытки вернул `200`, но это был лишь TLS fallback. Настоящий локальный VLESS smoke test получил `ConnectionResetError`; изолированный Xray уточнил отказ REALITY handshake. Причина несовместимости именно с `www.microsoft.com` до конца не установлена.
4. Изолированный тест с `www.cloudflare.com` прошёл. Одноразовая миграция сменила target и SNI с резервной копией настроек; рабочий VLESS smoke test затем вернул `VLESS traffic OK: TLSv1.3`. Новые установки используют Cloudflare по умолчанию.
5. iPhone импортировал новый профиль через QR. После первого долгого состояния «Отключение…» повторное выключение и включение в Hiddify дало соединение по LTE. `ipleak.net` показал исходящий IPv4 VPS `162.35.172.6`; видимые DNS-резолверы были Google, WebRTC — адрес VPS и локальный mDNS, IPv6-тест завершился тайм-аутом. Проверка Windows с новым профилем и kill switch остаётся открытой.

Не делайте вывод о работе VPN по `/readyz`, журналу запуска Xray или одному открытому порту. На VPS используйте `sudo python3 /opt/private-gateway-docker/current/docker/vpn-smoke.py`, затем проверьте реальное устройство и сеть. Не присылайте полный VLESS URI, UUID доступа или ключи в отчёте.

## Вход в панель и доступ к браузеру

После установки форма входа говорила «Токен недействителен» и на Windows, и на iPhone. Проверки показали, что токен в `stack.env` совпадал с токеном API, а авторизованный HTTPS-запрос к API возвращал `200`. Точная причина отказа формы не была установлена. Старый токен был раскрыт в переписке, поэтому его ротировали; после этого пользователь успешно вошёл в панель. Новый токен хранится только на VPS в `/etc/private-gateway-docker/stack.env` и не записан в репозиторий.

Раньше Caddy открывал отдельное системное окно Basic Auth: логин `browser` и серверный `GATEWAY_API_TOKEN`. Поэтому владелец видел второй запрос пароля после входа в панель. Теперь это окно устранено: noVNC принимает только cookie, связанный с сеансом администратора после проверки пароля и TOTP. Запрос `/browser/vnc.html` без такого cookie возвращает `403`; при правильном cookie, но остановленном browser worker возможен `502`. Внутренний CLI-токен не открывает публичный API и noVNC. После выхода из панели, смены пароля или перезапуска API откройте браузер заново через панель.

Позже на странице входа вновь отображалось поле `GATEWAY_API_TOKEN` вместо логина и пароля. Причина: новая страница получала `configured: false` из `/api/v1/auth/config` и показывала оставленную запасную форму. После удаления этой формы на странице показывались внутренняя SSH-команда и состояние первоначальной настройки — их тоже убрали. Теперь публичная страница всегда показывает только обычный вход по логину и паролю, `/api/v1/auth/config` удалён, а до создания учётной записи попытка входа получает общий отказ. Публичный API не принимает CLI-токен. Если после зелёного CD всё ещё видна старая форма, сравните версию релиза на VPS с коммитом и обновите страницу браузера; сама отправка коммита не подтверждает успешное развёртывание.

## Удалённый браузер

Внутренний smoke test подтвердил HTTP, WebSocket и VNC. Удалённый Chromium через `2ip.io` и `https://api.ipify.org/` показал IPv4 VPS. `api.ipify.org` — API, поэтому страница с одной строкой IP ожидаема; полноценный сайт находится на `https://www.ipify.org/`. Если вместо сайта открылась поисковая выдача, вводите полный URL в адресную строку **внутреннего Chromium**.

Внешний noVNC всё ещё иногда долго открывается и задерживает ввод/прокрутку на 1–3 секунды. Понижение качества noVNC и разрешения экрана до 1280×720 не решило проблему. Измерения во время активной прокрутки: CPU 1,2%, throttling 0 с, чтение диска 0 МБ за 15 с; ping с Windows — 0% потерь, 145–189 мс, среднее 163 мс. Ранее Docker показал 771 МБ из лимита 1 ГБ и 147 ГБ **накопленного** block I/O; текущий замер 0 МБ/15 с не подтверждает активную дисковую нагрузку. В локальном сравнении старый и альтернативный VNC-серверы отвечали примерно за 16 мс каждый, поэтому альтернативу не развёртывали. Первый замер сетевого трафика `0,0 МБ/15 с` мог быть сделан на однострочной странице IP без видимой прокрутки и не является выводом о пропускной способности сети. Причина внешней задержки окончательно не локализована; владелец решил пока оставить noVNC как есть.

Для обычного просмотра сайтов используйте локальный браузер с совместимым клиентом VLESS + REALITY. После использования удалённого браузера остановите сеанс в панели: это освобождает память и удаляет временный профиль.
