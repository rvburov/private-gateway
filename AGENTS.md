# AGENTS.md

Указания для ИИ-агентов (Claude Code, Codex, Copilot, Cursor и других), которые работают в этом репозитории. Здесь то, что нужно знать до первой правки; подробности — в [README.md](README.md) и [docs/](docs/), планы и принятые решения — в [docs/roadmap.md](docs/roadmap.md).

## Параллельная работа агентов — прежде всего

Пользователь ведёт одновременно несколько чатов Claude Code и других ИИ на ПК с Windows, а ещё Codex Cloud и Codex CLI на VPS. Ни одна работа не должна потеряться, и ни один агент не должен испортить работу другого, поэтому:

1. **В основной папке репозитория агенты не работают.** Каждый чат на ПК — в своей рабочей папке (git worktree) на своей ветке, даже если сейчас он один. В основной папке только `master`: сюда вливается готовая работа.
2. **В начале чата** — `bash scripts/worktree.sh check` (на Windows из Git Bash) и показать пользователю всё, что в итоге помечено: незакоммиченное, не влитое в `master`, не отправленное в GitHub, папки не на месте. Чужие папки и ветки не трогать.
3. **Своя папка** — внутри основной, в каталоге с точкой, который исключён в `.gitignore`:
   - **Claude Code** — `EnterWorktree` с именем: папка `.claude/worktrees/<имя>`, ветка `worktree-<имя>` от локального `master` (`worktree.baseRef` в `.claude/settings.json`);
   - **остальные ИИ на ПК** — `bash scripts/worktree.sh new <имя>`: папка `.agents/worktrees/<имя>`, ветка `<имя>`;
   - **Codex Cloud и Codex CLI на VPS** работают в своих копиях репозитория и рабочих папок не заводят: облачная задача уже изолирована, на VPS исходники лежат в `~/private-gateway`, а `/opt/private-gateway-docker/current` — установленный релиз, его не редактировать. Изменения между копиями ходят только через GitHub: перед push — `git fetch origin`, `git rebase origin/master`, `bash scripts/dev.sh test`, затем `git push origin HEAD:master` обычной перемоткой.

   Дальше работать только в своей папке. Имя — по сути задачи (`subscription-link`, `fix-apply`): латиница, цифры, дефис, до 20 знаков.
4. **«Сделай коммит» — это коммит и сразу перенос в `master`:** коммит в свою ветку → `bash scripts/worktree.sh sync` (ветка встаёт на свежий `master` или на `origin/master`, если копия Codex отправила что-то новее) → `bash scripts/dev.sh test` → `bash scripts/worktree.sh merge`. Если `merge` отказал, потому что `master` ушёл вперёд, — снова `sync`, тесты, `merge`. Сообщать пользователю «сделано» — только после строки `Merged ... into master`.
5. **push — только по отдельной просьбе пользователя,** в том числе из копий Codex: каждый push в `master` запускает CI и автоматическую выкладку на серверы. Перед push — `bash scripts/worktree.sh check`; если `origin/master` ушёл вперёд — `sync`, тесты и `merge`. Затем из основной папки `git push origin master` — только перемоткой.
6. **Перед последним ответом в чате** — снова `bash scripts/worktree.sh check` и назвать пользователю всё помеченное.
7. **Папку и ветку убирать только по слову пользователя** — `bash scripts/worktree.sh remove <имя>`, у Claude Code ещё `ExitWorktree` с `remove`: оба откажут, если есть незакоммиченное или не влитое. `discard_changes`, `git worktree remove --force`, `git branch -D`, `git reset --hard`, `git clean`, `git push --force` и удаление папок руками запрещены.
8. **В других местах проекта рабочих папок не создавать.** `check` помечает такие папки — показать пользователю.

Общее у всех папок на машине:

- **Проверки** каждой папки идут в своём наборе контейнеров Docker (имя — от имени папки), поэтому их можно запускать параллельно. Кеш сборки Go — общий том `private-gateway-checks-go-build`; не удалять его, пока идут чужие прогоны.
- **Рабочий VPS** один на всех: менять его вручную — только в задаче по эксплуатации или развёртыванию.

**Claude Code:** из рабочей папки он не пускает git в основную, поэтому `merge` так: `ExitWorktree` с `keep` → в основной папке `bash scripts/worktree.sh merge <имя>` → снова `EnterWorktree` с `path`, если работа продолжается. В рабочей папке он читает AGENTS.md своей ветки: правка AGENTS.md, влитая в `master`, доходит до чата после `sync`. Если при закрытии чата Claude Code спросит, оставить ли папку, а в ней не влитое, — оставить.

## Проект

Private Gateway — личный шлюз VLESS + REALITY с панелью управления и временным удалённым браузером. Xray передаёт трафик, Go API управляет устройствами и конфигурациями, PostgreSQL 18 хранит состояние, панель написана на React, TypeScript и Vite. Разработка идёт на ПК с Windows (Git Bash, Docker Desktop) и в копиях Codex; production — Docker Compose на VPS с Ubuntu 26.04 amd64.

Где что лежит:

- `cmd/gateway-api`, `cmd/gatewayctl` — API-сервер и CLI;
- `internal/` — пакеты Go: `httpapi` (API и раздача панели), `storage` (миграции и запросы sqlc; `internal/storage/db` генерируется), `xray` (конфигурация, применение, статистика), `adminauth`, `secure`, `browser`, `config`, `model`;
- `web/` — панель;
- `deploy/docker/` — production-стек: compose, Dockerfile, установка и обновление на VPS; `deploy/browser/` — удалённый браузер; `deploy/checks/` — образ и контейнеры проверок;
- `deploy/servers/` — серверы, на которые выкладывает CI/CD (`ИМЯ.conf`, только открытые данные), и открытый ключ выкладки `deploy-key.pub`;
- `scripts/` — проверки, выпуск, список серверов, добавление сервера, рабочие папки агентов;
- `docs/` — развёртывание, клиенты, приватность, [roadmap](docs/roadmap.md), [история ошибок](docs/troubleshooting.md).

## Инварианты

- Production — Docker Compose на Ubuntu 26.04 amd64: PostgreSQL 18, Go API, Xray, временный Chromium/noVNC, Caddy и HAProxy. Не возвращать host systemd/Podman как основной способ запуска.
- Go, `pgx/v5`, PostgreSQL 18 и SQL-запросы `sqlc`. SQLite не добавлять. После изменений SQL — `bash scripts/dev.sh sqlc` (sqlc 1.30.0 в Docker); файлы `internal/storage/db` вручную не редактировать.
- Xray передаёт трафик независимо от доступности PostgreSQL. Конфигурация меняется только после проверки настоящим Xray; при ошибке запуска возвращается предыдущий рабочий конфиг.
- Сохранять различие между желаемой и применённой ревизиями. Создание и отзыв устройства требуют успешного применения к работающему Xray. Один ответ порта 443 или `/readyz` не доказывает, что VLESS-профиль работает.
- Удалять устройство можно только после отзыва и равенства желаемой и применённой ревизий. Неизменяемый аудит хранит UUID удалённого устройства без секрета профиля; удаление не перезапускает Xray и не меняет ревизию.
- На TCP 443 HAProxy направляет SNI панели в Caddy, остальные TLS-соединения — в Xray с VLESS + REALITY. Панель и noVNC доступны по обычному HTTPS без номера порта; 8443 оставлен для перенаправления старых ссылок. Внутренние API, PostgreSQL, Xray StatsService, browser worker и VNC наружу не публиковать.
- Production-браузер — в отдельном Docker-контейнере с непривилегированным UID, без Docker socket, host mounts и шлюзовых секретов; его профиль временный. Текущую скорость noVNC владелец принял; исправленной её не называть.

## Секреты и данные

- Токены, пароли, закрытые SSH/REALITY-ключи, VLESS URI и QR-коды не хранить в Git, документации, аудит-журнале, URL веб-запросов или аргументах процессов. Не просить прислать их в чат. Профиль выдавать только отдельной авторизованной операцией.
- Исключение по решению владельца — ссылка-подписка `https://ДОМЕН/sub/…`: её секрет по замыслу находится в пути URL, и по ссылке профиль выдаётся без входа. В базе хранится только SHA-256 секрета, сам он выводится из главного ключа. Не писать его в журналы и аудит, не включать журнал запросов Caddy; журнал ошибок Caddy пишет запросы без URI — фильтр не убирать.
- Публичная страница входа не должна раскрывать внутренние команды VPS или состояние первоначальной настройки администратора. Эксплуатационные команды держать в закрытом рабочем процессе и документации для владельца.
- Публичный API принимает только временный сеанс, выданный после проверки логина, пароля и TOTP; до настройки учётной записи публичного входа нет. Логин и хеш пароля хранятся в PostgreSQL; TOTP подключается и подтверждается в браузере, после чего его секрет хранится в базе зашифрованным. Секрет не печатать в терминале. Долгоживущий `GATEWAY_API_TOKEN` оставлен только для локального CLI внутри API-контейнера. Caddy допускает к noVNC только по отдельному короткоживущему cookie, связанному с подтверждённым сеансом администратора; без второго фактора обхода быть не должно. Смена логина и пароля выполняется только root-командой на VPS с backup и откатом и требует нового подключения 2FA в браузере.
- GitHub Secrets содержат только закрытый ключ выкладки `DEPLOY_SSH_KEY`; адреса серверов и ключи их хостов — открытые данные в `deploy/servers`. Секреты приложения находятся на каждом сервере в `/etc/private-gateway-docker/stack.env`; локальный `.env` на ПК GitHub Actions не читает и в образ проверок не попадает. При раскрытии действующего секрета ротировать его и проверить доступ без вывода нового значения.
- Для backup нужны согласованные копии базы **и** ключей из env. Не удалять старую установку и backups до проверенного восстановления.

## Проверки

```bash
bash scripts/dev.sh test    # все проверки в Docker; на Windows — из Git Bash при запущенном Docker Desktop
bash scripts/dev.sh sqlc    # после изменения SQL-запросов или миграций: sqlc 1.30.0 в Docker
bash scripts/dev.sh release DIR   # релиз закоммиченной версии в том же образе (так собирает CI)
```

- **Тесты гонять всегда:** перед коммитом — `bash scripts/dev.sh test`. В отчёте — числа прогона; упавшее или пропущенное не выдавать за прошедшее.
- Нужен только Docker. Образ [deploy/checks/Dockerfile](deploy/checks/Dockerfile) содержит Go 1.26.9, Node.js 22, Python, настоящий Xray 26.3.27, sqlc 1.30.0 и actionlint 1.7.12, загрузки сверяются по SHA-256. PostgreSQL 18 работает рядом во временном контейнере без открытых портов.
- Образ собирается из содержимого будущего коммита: отслеживаемые файлы с правками и новые неигнорируемые, с переводами строк репозитория (LF) независимо от `core.autocrlf`. `.env` и другие игнорируемые файлы в образ не попадают.
- Входят `sqlc diff`, `go vet`, `go test -race` с PostgreSQL и Xray, сборка программ, тесты и сборка панели, `actionlint` для workflow, синтаксис и тесты скриптов выпуска, развёртывания и списка серверов. Внутри Docker интеграционные тесты не пропускаются молча: пропуск из-за `TEST_DATABASE_URL` или `PRIVATE_GATEWAY_REAL_XRAY_BINARY` проваливает прогон.
- Сборку production-образов, проверки Caddy и HAProxy (`test-browser-proxy.py`, `test-edge-router.py`, `test-first-deploy.sh`) и тест установки, обновления и отката (`test-install-update.sh`, только на runner Ubuntu 26.04) выполняет GitHub Actions при push любой ветки; локально они не идут, так и писать в отчёте. Для релизных и деплойных изменений проверять связанные скрипты и Docker-конфигурацию.
- Первый прогон скачивает около 2 ГБ образов; повторные переиспользуют слои и кеш сборки Go.
- Локальный запуск API и панели (`bash scripts/dev.sh prepare|start|stop`) пока требует Linux с Go и Xray.

## Выпуск: CI/CD

- Каждый push в `master` запускает CI (`verify`: те же проверки в Docker, что `bash scripts/dev.sh test`, затем релиз, production-образы и тест установки, обновления и отката) и сразу после него выкладку на все серверы из `deploy/servers` — задания `Deploy Docker to VPS (ИМЯ)`; так решил владелец. Поэтому в `master` не отправлять экспериментальное или частично проверенное, а push делать только по его просьбе.
- Push ветки своей папки (`git push origin HEAD`) запускает тот же `verify` без выкладки: так изменения выпуска и развёртывания проверяют на GitHub до `master`. Тоже только по просьбе пользователя.
- После выкладки GitHub проверяет `https://ДОМЕН/readyz` снаружи с проверкой TLS. Это подтверждает панель, но не VLESS-профиль на устройстве.
- Новый сервер добавляет только владелец: `bash scripts/add-server.sh` в основной папке требует сверить отпечаток ключа хоста и ввести пароль `sudo` на сервере. Агент записи в `deploy/servers` сам не создаёт и не меняет.
- После push различать зелёный `verify`, зелёный `Deploy Docker to VPS (ИМЯ)` для каждого сервера и фактическую проверку сервиса. Статус смотреть через GitHub CLI (`gh run list --branch master`, `gh run view ID`); если `gh` не установлен или без входа — прямо говорить, что статус не подтверждён.
- Не менять production VPS, firewall, SSH и службы вручную вне задачи по эксплуатации или развёртыванию. При авторизованном развёртывании — только проверенный релиз, с TLS-проверкой, подписями пакетов и контрольными суммами. Проверки ради успешного запуска не отключать.
- Ошибка при обновлении требует проверки backup и текущего состояния перед повтором. Рабочую базу не удалять через `docker compose down --volumes` при обычной остановке; временный стек проверок `deploy/checks` удаляется целиком — так задумано.

## Работа с пользователем

- Все сообщения пользователю — по-русски; английский только в идентификаторах, путях и цитатах из кода.
- **Прежде чем что-то менять — спросить.** Перед правкой файлов, запуском контейнеров, коммитом, push или действиями на сервере коротко описать план и получить согласие; одобренный план выполнять без повторных вопросов о мелочах. Читать файлы и выполнять проверки, которые ничего не меняют, можно сразу.
- **Развилки решает пользователь:** поведение, названия, способ выкладки, порядок работ. Спрашивать 1–4 вопросами с готовыми вариантами, рекомендованный — первым. Технические мелочи внутри одобренного плана решать самому и называть в отчёте.
- Принятые решения записаны в [docs/roadmap.md](docs/roadmap.md) — не переигрывать их без пользователя.
- Работать самому, без подагентов и многоагентных разборов, пока пользователь прямо не попросит.
- Инструкция пользователю — один путь по шагам: где выполняется команда (Windows PowerShell, Git Bash, SSH на VPS, рабочая папка), что ввести и какой результат ожидать; без показа секретов.
