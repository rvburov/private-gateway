# Второй вход VLESS + XHTTP + REALITY

Внутренняя документация разработки и эксплуатации. Старый вход TCP + REALITY +
Vision сохраняется. Новый вход включается отдельно; наличие кода и ссылки-примера
не означает, что он уже работает на VPS или проверен на устройстве владельца.

## Назначение

XHTTP позволяет переносить новые потоки через повторно используемые соединения
между клиентом Xray и сервером. С REALITY закреплённое в проекте ядро Xray 26.3.27
использует HTTP/2; при `mode=auto` без отдельного download-подключения выбирается
`stream-one`. Пул XMUX принадлежит работающему клиенту: его перезапуск теряет прогрев.

Цель — уменьшить задержку новых соединений. Сокращение с четырёх RTT до двух,
например с 470 до 250 мс при RTT около 120 мс, является проверяемой гипотезой,
а не гарантированным результатом. Соединение VPS с сайтом и HTTPS приложения до
сайта всё ещё могут создаваться заново. DNS, потери, нагрузка и обработка сайтом
также входят во время до первого байта. Пинг и скорость скачивания не становятся
лучше автоматически; несколько потоков HTTP/2 зависят от общего TCP-соединения.

## Два транспорта, одна подписка

| Свойство | TCP + REALITY + Vision | XHTTP + REALITY |
| --- | --- | --- |
| Роль | Существующее подключение и совместимость | Дополнительный вариант для проверки задержки новых соединений |
| Внешний порт | Текущий порт узла, совместимый вход сохранён | Отдельный настраиваемый TCP-порт, по умолчанию 8444 |
| Flow | `xtls-rprx-vision` | Отсутствует |
| REALITY | Существующие ключ и short ID | Отдельные ключ и short ID; тот же SNI и target |
| Путь XHTTP | Не используется | Случайный, сохраняется между обновлениями |
| Пользователь | Существующий UUID устройства | Тот же UUID |
| Совместимость | Клиент должен поддерживать VLESS + REALITY + Vision | Клиент должен поддерживать VLESS + XHTTP + REALITY и импорт этих параметров |

Для устройства остаётся одна каноническая ссылка-подписка и прежний токен.
Общий список base64 при включённом XHTTP содержит сначала XHTTP, затем TCP с
отметкой `TCP Vision`. Наличие двух записей не включает автоматический failover:
выбор профиля и переключение зависят от приложения.

Известные клиенты Hiddify, sing-box, Clash/Mihomo и Stash сохраняют прежнюю выдачу
TCP. JSON sing-box и YAML Mihomo не заменяются на неподтверждённый XHTTP-формат.
Явный `format=uri` по-прежнему возвращает одну TCP-ссылку. User-Agent используется
только для сохранения совместимости формата, а не как доказательство возможностей
любой версии. Без включённого XHTTP выдача остаётся прежней.

Неизвестный клиент получает общий список, если функция включена и применена.
Старые версии могут не импортировать XHTTP или весь смешанный список. В таком
случае используется отдельный TCP URI/QR либо прежний совместимый формат из той
же панели. Совместимость неизвестных версий не считается подтверждённой.

В авторизованном окне профиля доступны все прежние форматы и дополнительный
XHTTP URI/QR, если вход настроен. У выбранного профиля показаны транспорт, защита,
порт и пояснение совместимости. До настоящих замеров задержка обозначена как
«Не измерено»; постоянных ярлыков «быстрая» и «медленная» нет. Выбор в панели
меняет копируемый профиль и QR, а не переключает VPN на устройстве.

## Настройки и секреты

| Переменная | Значение и назначение |
| --- | --- |
| `GATEWAY_XHTTP_ENABLED` | `0` по умолчанию, `1` включает второй вход |
| `GATEWAY_XHTTP_PORT` | TCP-порт, по умолчанию 8444; должен отличаться от занятых портов шлюза и статистики |
| `GATEWAY_XHTTP_PRIVATE_KEY` | Отдельный закрытый X25519-ключ REALITY |
| `GATEWAY_XHTTP_SHORT_ID` | Отдельный short ID |
| `GATEWAY_XHTTP_PATH` | Случайный URL-путь с одним сегментом, не короче 16 символов после `/` |

Закрытые значения находятся только в защищённом окружении VPS и рабочем конфиге
Xray. Помощник создаёт их на месте; выводить их в терминал или передавать в чат
не нужно. Повторная настройка сохраняет существующие значения. Публичный ключ
вычисляется из закрытого; профиль выдаётся только авторизованной операцией или
по секретной подписке устройства. Ключи, UUID, настоящие адреса и случайные пути
не включают в новые примеры, фикстуры, журналы и отчёты.

Оба входа получают единый список активных устройств. Отзыв и успешное применение
конфигурации исключают устройство из обоих входов. Новый независимый список
пользователей не создаётся. Изменение настроек проходит через существующие
желаемую и применённую ревизии и проверку настоящим Xray.

## Включение после установки проверенного релиза

Выполняется владельцем через SSH на VPS с уже установленным релизом, содержащим
помощник XHTTP. Перед этим должна быть доступна проверенная копия конфигурации и
способ восстановления подключения. Рабочие UUID и старые ключи сбрасывать не нужно.

```bash
sudo python3 /opt/private-gateway-docker/current/docker/configure-xhttp.py --enable --port 8444 --apply
```

Помощник готовит секреты и резервные копии, проверяет Compose, применяет настройки
через API/Xray и проверяет оба транспорта. Перед сообщением об успехе он ждёт
доступности канонической HTTPS-панели через HAProxy и Caddy не более 60 секунд,
с проверкой сертификата. Локальная готовность API-контейнера этого не заменяет.
При ошибке восстанавливает прежние файлы и пытается вернуть работающее состояние,
включая проверку HTTPS-панели после отката. Применение может кратковременно
прервать подключения: оба входа обслуживает общий процесс Xray.

Без `--apply` команда только готовит окружение для последующего применения;
работающий вход этим не подтверждён. Обычный updater может пропустить повторную
выкладку того же SHA, поэтому для применения на установленном релизе используется
именно `--apply`, а не повтор updater без изменений.

Порт публикуется только при включённом XHTTP, через отдельный Compose overlay,
только как TCP. Выключенная функция не резервирует дополнительный host-порт.
Разрешение этого TCP-порта во внешнем
брандмауэре VPS или панели хостинга проверяется отдельно. Публикация Docker-порта
не доказывает доступность из сети клиента; UDP-порт для внешнего HTTP/2 не нужен.
Внутренние API, статистика, база и VNC не публикуются.

Для возврата к прежней схеме:

```bash
sudo python3 /opt/private-gateway-docker/current/docker/configure-xhttp.py --disable --apply
```

После применения заново получите профиль в панели или обновите существующую
подписку в клиенте. Совместимость конкретного приложения и версии проверяется
на устройстве. Удалять TCP + Vision можно только отдельным последующим решением,
когда все необходимые клиенты и сценарии подтверждены.

## Функциональные проверки

- `xray run -test -c …` проверяет синтаксис и настройки, но не передачу трафика.
- Серверный smoke отдельно проверяет старый TCP и новый XHTTP, если он включён.
- Проверка нового клиента должна действительно открыть сайт через XHTTP.
- Отдельно проверяются прежние ссылки, экспорт, подписка, отзыв устройства,
  обновление, ошибка применения и возврат к прежней конфигурации.
- Локальный loopback-тест подтверждает функцию, но не доступность порта через
  оператора клиента и не ускорение маршрута до удалённого VPS.

## Сравнение задержки на устройстве клиента

Проводить в той сети, где нужен выигрыш. Клиент на самом VPS не воспроизводит
пользовательский RTT. Сначала записать версии приложений/ядер и настройки режима.

1. Запустить два постоянно работающих клиента Xray: TCP и XHTTP, с локальными
   SOCKS-входами только на loopback и разными портами, например 1080 и 1081.
   Рабочие профили брать из защищённого окна панели; не сохранять их в репозиторий.
2. Не перезапускать эти клиенты между запросами. Сравнение выполняется отдельными
   процессами curl, чтобы новые прикладные соединения открывались при живом пуле Xray.
3. Из корня репозитория на клиентском устройстве запустить:

```bash
python3 scripts/benchmark-transports.py --tcp-socks 127.0.0.1:1080 --xhttp-socks 127.0.0.1:1081 --requests 10 --warmup 1
```

Нужны Python 3 и curl. По умолчанию проверяется HTTPS `generate_204` Cloudflare.
Первая проба учитывается отдельно; холодной она будет только после заведомо
нового клиента, который ещё не передавал трафик. Затем идёт прогрев и по десять
измеряемых запросов для каждого транспорта. Порядок TCP/XHTTP чередуется.
Ошибки, тайм-ауты и неожиданные HTTP-коды не превращаются в быстрые успешные
результаты. Отчёт показывает число успехов и ошибок, медианы и изменение времени.

Это измерение до первого байта, включающее маршрут и ответ целевого сервиса.
Сам номер запроса не доказывает повторное использование соединения. Режим и
поведение XMUX нужно подтвердить отдельно без записи секретов и адресов в журнал.
При изменчивой мобильной сети полезны несколько серий; после теста задержки
отдельно проверить параллельную загрузку, длительный сеанс и стабильность.

## Обезличенный пример для Private Gateway Client

Фикстура [vless-xhttp-reality.txt](examples/vless-xhttp-reality.txt) предназначена
только для разбора ссылки и проверки импорта. В ней TEST-NET-адрес, `example.com`,
заранее известные тестовые UUID/ключ/short ID/путь; подключаться по ней нельзя.

Файл можно перенести в клиентский репозиторий как
`shared/testdata/links/vless/vless-xhttp-reality.txt`. Клиентский репозиторий в эту
задачу не входит: перенос и тесты его парсера здесь не считаются выполненными.
Проверить `type=xhttp`, `security=reality`, `mode=auto`, декодирование `path`,
SNI, fingerprint, публичный ключ, short ID, порт, имя с XHTTP и отсутствие `flow`.

## Границы подтверждения

Фактические результаты локальных тестов, CI, серверного smoke и клиента записывают
раздельно в [roadmap](roadmap.md). Сама реализация не подтверждает включение на VPS.
Серверный smoke не подтверждает поддержку всех приложений, повторное использование
соединения или выигрыш задержки на телефоне.
