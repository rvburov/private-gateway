# Постоянный IP для личного VPN

Внутренняя документация разработки Private Gateway. Обновлено 28 октября 2026.
Документ хранится в репозитории и не добавляется в страницы, меню или статические
файлы сайта. Условия конкретных компаний и результаты нашего поиска вынесены в
[справочник провайдеров](proxy-providers.md).

## Цель и текущее состояние

Нужен один выделенный постоянный IPv4 США с подходящей ISP-классификацией для
выхода личного VPN. Он должен обслуживать нужный TCP- и UDP-трафик, сохраняться
при переподключении и своевременном продлении, иметь понятные ограничения и цену.

Исходный VPS — InterServer с адресом `162.35.172.6`, штат Нью-Джерси, США. Его IP
относится к дата-центру. Сам VPS можно оставить точкой входа VPN и при необходимости
направлять его исходящий трафик через отдельный ISP-прокси.

Полностью проверенного подходящего прокси пока нет. Через ROLA прошёл отдельный
TCP-запрос; у купленного адреса IPRoyal SOCKS5-запрос завершался тайм-аутом. Общая
маршрутизация VPN через эти прокси в ходе поиска не настраивалась. Команды проверки
с `curl --proxy` действовали только на соответствующий запрос.

## Основные понятия

| Понятие | Простое объяснение |
| --- | --- |
| Публичный IP | Адрес источника соединения, который видит внешний сайт. Он может отличаться от адреса устройства внутри домашней сети. |
| VPS | Виртуальный сервер: на нём можно запускать VPN, приложения и терминал. Сам по себе VPS не предоставляет домашнее подключение. |
| Прокси | Посредник для передаваемых через него запросов. Покупка прокси обычно даёт адрес подключения, порт и способ авторизации, а не доступ к полноценному компьютеру. |
| IP дата-центра, Datacenter / DCH | Адрес сети серверного хостинга. Это обычная классификация VPS; сама по себе она не означает утечку или вредоносность. |
| Домашний широкополосный IP, Residential / Broadband | Адрес подключения через сеть домашнего интернет-провайдера. Правильное слово — «широкополосный». |
| ISP / Static Residential | Название коммерческого прокси-продукта с адресами интернет-провайдеров. Оборудование может находиться в дата-центре; название не доказывает размещение в жилом доме. |
| Статический IP | Адрес остаётся одним и тем же в согласованный срок. Условия переподключения, продления и изменения тарифа нужно проверять отдельно. |
| Выделенный IP, Dedicated / Exclusive | Адрес закреплён за одним клиентом провайдера. Это свойство адреса, а не обещание отдельного физического компьютера. |
| Shared | Один выходной адрес могут использовать несколько клиентов. |
| Ротация | Выходной IP меняется автоматически или по запросу. Для нашей цели не нужна. |
| Sticky session | Временное закрепление адреса на сессию. Оно не равно сохранению одного выделенного IP на месяцы. |

По длине IP и отдельным цифрам нельзя определить его страну, провайдера или тип.
Для этого нужны сведения о диапазоне и конкретном адресе из баз, условия услуги
и проверка фактического подключения.

## Четыре способа подключения

### 1. Прямой выход через VPS

Устройство → VPN на VPS → сайт.

Сайт видит выходной IP VPS для переданного через него трафика. Это исходная схема
нашего шлюза. Дополнительный адрес того же дата-центра не становится домашним из-за
смены настроек, reverse DNS или установки другой программы.

### 2. Удалённая работа на физическом компьютере

Устройство → удалённый экран или SSH → компьютер с домашним интернетом → сайт.

Браузер или CLI, запущенные на удалённом компьютере, обращаются к сервисам через
его сетевой выход. Браузер и другие программы на собственном устройстве продолжают
использовать свои маршруты. Удалённый рабочий стол не включает VPN для всего
локального устройства автоматически. Это относится и к CLI Claude: значение
имеет место запуска процесса и маршрут именно его запросов.

Само наличие физического компьютера ничего не говорит о типе сети: компьютер в
дата-центре также может иметь серверный IP. Для домашнего варианта существенны
реальное подключение к домашнему провайдеру и условия адресации.

### 3. Собственный VPN или прокси на домашнем компьютере

Устройство → VPN/прокси на домашнем компьютере → сайт.

Так можно передавать трафик своего устройства через домашний интернет удалённого
узла. Для полного туннеля нужно настроить маршрутизацию, DNS, IPv6 и поведение при
обрыве; доступ к одному удалённому экрану этого не обеспечивает.

Для такого узла нужны:

- согласие владельца компьютера и подключения, разрешённое условиями провайдера использование;
- постоянное питание, работа без сна и возможность восстановления после перезагрузки;
- достаточные скорость и стабильность, в том числе исходящая скорость домашнего канала;
- защищённое удалённое администрирование и обновления;
- способ достичь узла: публичный доступный адрес либо отдельно настроенный исходящий туннель;
- договорённость о постоянном внешнем адресе, если он требуется.

Домашний IP может быть динамическим. DDNS помогает найти меняющийся адрес, но не
делает его постоянным для сайтов. При CGNAT несколько абонентов могут делить один
публичный IP, а обычный проброс порта на роутере не обеспечивает входящий доступ.
Возможность статического выделенного публичного IPv4 уточняют у интернет-провайдера.

### 4. VPS с прокси коммерческого провайдера

```mermaid
flowchart LR
    Device["Твоё устройство"] -->|"VPN"| VPS["Личный VPS"]
    VPS -->|"Настроенный выход"| Proxy["Постоянный ISP-прокси"]
    Proxy --> Site["Сайт"]
```

IP VPS служит адресом входа для VPN-клиента. IP прокси — адресом выхода для
направленного через него трафика. Это два разных назначения; купленный прокси-IP
обычно не назначают сетевому интерфейсу VPS.

Провайдер сообщает точные адрес, порт и авторизацию подключения. Адрес входа в
прокси может отличаться от выходного IP, видимого сайту. В частности, некоторые
услуги используют доменное имя шлюза и отдельный порт для каждого назначенного IP.
Нельзя подменять эти параметры предположением по адресу, увиденному в IP-базе.

| Вариант | Что получает пользователь | Основное ограничение |
| --- | --- | --- |
| VPS напрямую | Собственный сервер и его сетевой выход | Обычно классификация дата-центра |
| Удалённый домашний ПК | Рабочий стол или терминал другой машины | Локальные приложения не переходят на этот выход автоматически |
| VPN на домашнем ПК | Возможность направить через домашнюю сеть трафик устройства | Постоянная работа узла, доступность сети и администрирование |
| VPS + ISP-прокси | Управляемый VPN и покупной постоянный выход | Ограничения и надёжность прокси-провайдера |

## Требования к прокси для нашего VPN

| Параметр | Что нужно получить или уточнить |
| --- | --- |
| Страна и адрес | Один публичный IPv4 США; фактическую геолокацию проверяем по нескольким источникам |
| Продукт | Dedicated Static ISP / Static Residential; название сопоставляем с классификацией конкретного IP |
| Эксклюзивность | Другие клиенты провайдера не используют этот IP во время нашего заказа |
| Постоянство | Нет ротации; адрес сохраняется после переподключения и своевременного продления |
| Протоколы | TCP и стандартный SOCKS5 UDP ASSOCIATE, совместимый с выходом Xray |
| Выход TCP и UDP | Один и тот же ожидаемый публичный IP |
| Допустимое использование | Личный VPN на Linux VPS прямо разрешён провайдером |
| Порты и сайты | Доступны нужные TCP/UDP-порты и сервисы; нет несовместимого с нашими задачами списка разрешений |
| Скорость | Приемлемые реальные скорость, задержка и стабильность из сети нашего VPS |
| Трафик и соединения | Понятны квота, учёт загрузки/отдачи, fair use и последствия превышения |
| Полная стоимость | Минимальный платёж, число IP, срок, доплаты, автопродление и сохранение IP |
| Тест и обслуживание | Условия пробного заказа, замены неисправного IP и возврата до использования |

TCP нужен, например, для обычных HTTPS-запросов. UDP используется в части DNS,
звонков, игр и других сетевых протоколов. Требование UDP здесь относится к цели
обслуживать весь нужный личный VPN; для одного CLI с HTTPS оно само по себе не
обязательно.

SOCKS5 передаёт поддерживаемый TCP- и UDP-трафик, но не произвольные IP-протоколы,
например ICMP. Поэтому «весь VPN» в этой схеме означает нужный поддерживаемый
трафик приложений. Неудачный `ping` сам по себе не доказывает неисправность прокси.

Надпись SOCKS5 не гарантирует UDP. Общего ответа «UDP есть» недостаточно, если
стандартная команда UDP ASSOCIATE отсутствует или доступна в другом продукте.
Нельзя переносить свойства Datacenter на ISP, а rotating Residential — на Dedicated ISP.

Числовой бюджет и требуемый месячный объём трафика пока не определены. Их нужно
сопоставить с фактическим минимальным заказом, а не только ценой «от … за IP».

## Постоянный выход и резерв

Для постоянства адреса предполагается один основной ISP-прокси. Прямой выход VPS
можно предусмотреть как ручной резерв или режим диагностики. Автоматический
незаметный переход на VPS изменит внешний IP.

Если сохранение адреса важнее доступности, при отказе прокси трафик должен
блокироваться, а не уходить напрямую. Такое поведение требует отдельной реализации
и проверки; в текущем поиске оно не настраивалось.

Смена IP не скрывает cookies, вход в аккаунт, язык, часовой пояс или отпечаток
браузера. Внешний сервис принимает решение по собственной совокупности данных;
оценка IP-базы не является оценкой Claude или обещанием доступа к нему.

## Страна VPS, скорость и задержка

VPS в Финляндии может использовать прокси США. При этом нужно оценивать полный
маршрут: пользователь → VPS → прокси → целевой сервис.

Близость VPS и прокси, например один регион США, сокращает расстояние между ними,
но может увеличить путь пользователя до VPS. Совпадение страны не гарантирует
лучший маршрут: внутри США также большие расстояния. Решение принимают по
измерениям в нужной сети.

Пропускная способность ограничивается самым медленным участком и лимитами тарифа.
Задержка влияет на начало ответа и интерактивность. Большая задержка может
сосуществовать с быстрым скачиванием большого файла.

Сначала используем имеющийся InterServer в Нью-Джерси для сравнения. Покупка нового
VPS до измерений не требуется. Для ориентира: канал 10 Мбит/с соответствует максимум
примерно 1,25 МБ/с до протокольных накладных расходов.

## Безопасность и границы доверия

Сами по себе страны VPS и прокси не определяют безопасность. Важны защита каждого
участка, настройка маршрутов и доверие к операторам.

Обычный SOCKS5 не шифрует соединение VPS → прокси, включая собственную парольную
аутентификацию. Шифрование VPN между устройством и VPS заканчивается на VPS и не
защищает следующий участок автоматически. Если провайдер поддерживает защищённый
транспорт до прокси, его совместимость и настройку проверяют отдельно.

HTTPS продолжает шифровать содержимое между приложением и сайтом при штатной
проверке сертификата. Прокси всё равно может видеть адреса назначений, время и
объём соединений; незашифрованный прикладной трафик может быть доступен посреднику.
Прокси-провайдер также видит соединение от VPS.

Логины, пароли, ключи и полные строки доступа не включают в документацию, отчёты
или команды с секретами в аргументах. Их не запрашивают в переписке. Проверки не
должны требовать отключения TLS-проверки или установки неизвестного корневого сертификата.

## Как читать результаты IP-баз

| Источник или поле | Что показывает | Чего не доказывает |
| --- | --- | --- |
| IP2Location, IPinfo и аналогичные базы | Географию, сеть, владельца и доступную классификацию | Точную физическую квартиру, скорость или работоспособность прокси |
| `usage_type` / `as_usage_type` | Тип конкретного IP / тип всей автономной системы | Эти два значения не обязаны совпадать |
| `net_speed`, DSL, T1 | Категорию в базе | Фактическую измеренную скорость |
| `is_vpn`, `is_proxy` | Наличие отметки в конкретном наборе данных | Значение `false` не доказывает отсутствие фактического VPN/прокси |
| `is_residential_proxy` | Отметку об известной residential proxy-сети | Значение `false` не является самостоятельной классификацией домашнего доступа |
| Fraud score | Оценку по методике выбранного источника | Универсальную оценку IP или решение конкретного сайта |

Отсутствующее поле не равно `false` или нулю. География и классификации могут
различаться и устаревать. Баллы разных баз не усредняют. Если источник применил
общую оценку оператора из-за отсутствия наблюдений конкретного адреса, это отдельно
фиксируют. Низкий риск может сочетаться с отметкой VPN.

Отзывы о компании рассматривают отдельно от характеристик адреса и проверки
соединения. Методика сравнения Proxyway, G2 и Trustpilot находится в
[справочнике провайдеров](proxy-providers.md).

## Порядок проверки перед подключением всего VPN

1. **Условия услуги.** Подтвердить точный продукт, назначение, разрешённые порты,
   постоянство и стоимость. Выяснить лимиты тестирования и возврата до передачи данных.
2. **Параметры подключения.** Взять из кабинета точные адрес, SOCKS5-порт и способ
   авторизации. Открытый TCP-порт означает только доступность TCP-соединения.
3. **TCP и выход.** Выполнить короткий HTTPS-запрос через прокси и получить
   фактический внешний IP. Сравнить его с назначенным, затем проверить сведения баз.
4. **UDP.** Совместимым инструментом выполнить SOCKS5 UDP ASSOCIATE и обмен
   датаграммами с отвечающим сервисом. Фактический UDP-выход должен подтвердить
   удалённый сервис или его журнал; адрес relay в ответе SOCKS5 сам по себе не
   доказывает совпадение с TCP-выходом.
5. **Нужные сервисы.** Проверить доступ к необходимым сайтам и портам в пределах
   разрешённого использования.
6. **Скорость и стабильность.** Сравнить прямой выход VPS и прокси из одной сети,
   повторить короткие замеры в близкое время. Учитывать квоту и трафик тестов.
7. **Настройка VPN.** Только после отдельных тестов подготовить и проверить маршрут
   через прокси, сохранив проверяемый способ восстановления прежней конфигурации.
8. **Клиент.** Проверить на реальном устройстве выход TCP/UDP, DNS, IPv6, WebRTC,
   приложения вне браузера и поведение при обрыве.

`curl --proxy socks5h://… https://…` проверяет TCP и разрешение имени через прокси,
но не UDP. Локальный UDP-слушатель также не доказывает удалённый обмен UDP.
По тексту тайм-аута без дальнейшей диагностики нельзя заключить, что пароль неверен
или весь провайдер неисправен.

После завершения отдельного `curl --proxy` отключаться от прокси не нужно: эта
команда не меняет маршрутизацию VPS постоянно. Полный VPN и команды конкретных
программ проверяют независимо.

Текущая диагностика панели ориентирована на действующую схему шлюза. Перед будущим
включением внешнего прокси нужно проверить смысл сравнения с ожидаемым адресом
выхода: отличие от IP входа VPS само по себе может быть предусмотрено схемой.
Описание существующих тестов — в [проверках приватности](privacy-checks.md),
реальные результаты и дальнейшие вопросы — в [справочнике провайдеров](proxy-providers.md).
