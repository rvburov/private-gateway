# Развёртывание на VPS через Docker

Основной способ установки — Docker Compose на Ubuntu 26.04 amd64. Стек содержит PostgreSQL 18, Go API с панелью, Xray, временный Chromium/noVNC, Caddy и HAProxy. На сервере не нужны Go и Node.js: GitHub Actions собирает проверяемый архив и доставляет его по SSH на каждый сервер из папки `deploy/servers`. На текущем VPS (`main`) первая установка уже выполнена: панель открывается, конфигурация Xray применена, серверный VLESS-тест прошёл, а iPhone подключился через Hiddify по LTE. Новый сервер готовит одна команда [`scripts/add-server.sh`](#новый-сервер); после установки Docker сам поднимает контейнеры после перезагрузки.

Для текущего VPS используйте IPv4 `162.35.172.6` и домен панели `rb-gateway-3708079.duckdns.org`. Домен должен возвращать этот IPv4. TCP 443 принимает HAProxy: обращения к домену панели идут в Caddy, а VLESS + REALITY — в Xray. Caddy использует порт 80 для выпуска сертификата; старый порт 8443 перенаправляет на обычный адрес панели. SSH остаётся на порту 22. Убедитесь в панели провайдера, что входящие TCP 22, 80, 443 и 8443 разрешены. Дополнительные порты API, PostgreSQL, браузера и noVNC наружу не публикуются. На том же домене работают ссылки-подписки `https://ДОМЕН/sub/…` ([клиенты](clients.md#ссылка-подписка)): их секрет — в пути, поэтому у Caddy нет журнала запросов, а журнал ошибок пишет запросы без URI.

## Уже выполненный переход с прежней установки

По решению владельца была выполнена чистая Docker-установка с новым набором устройств, базой и ключами. Установщик сначала проверяет архив, собирает образы и запускает новую БД и API. Перед переключением портов он сохраняет конфигурацию и дамп старой базы в `/var/backups/private-gateway/`, затем останавливает старые службы. Если проверка Docker не проходит, он возвращает старые службы и удаляет незавершённый новый стек. После успеха старые файлы и учётные записи остаются для отката. **Старые профили VLESS с новой установкой не работают.** Для нового устройства нужен новый профиль; обычные последующие Docker-обновления сохраняют существующие устройства и ключи.

В репозитории удалены прежний systemd-установщик и Podman worker. Старый выделенный SSH deploy-key переиспользуется: временный приёмник разрешает только передачу проверенного релиза, затем установщик заменяет его обработчиком обновлений Docker. После каждого коммита в `master` workflow **CI/CD** проверяет код, собирает релиз и только после успеха отправляет его на каждый сервер из списка. При ошибке проверок развёртывания не будет. Если более новый коммит уже попал в `master`, устаревший релиз не развёртывается.

## Повседневная работа с текущим VPS

1. Откройте панель `https://rb-gateway-3708079.duckdns.org/`. После [настройки учётной записи](#учётная-запись-администратора) входите по логину, паролю и коду приложения-аутентификатора. До настройки учётной записи публичного входа нет. Не отправляйте учётные данные в переписку и не вставляйте пароль или код в аргументы команд.
2. После создания или отзыва устройства нажмите в панели «Проверить» и «Применить конфигурацию». Убедитесь, что новая и применённая ревизии совпали. Для нового устройства откройте «Профиль»: скопируйте стандартную VLESS-ссылку или покажите QR-код и импортируйте в [совместимый клиент](clients.md). Проверьте внешний IP на устройстве. QR, URI и конфигурационные файлы содержат секрет доступа.
3. Для обновления проекта достаточно готового коммита в `master`: Actions выполняет `verify`, затем `Deploy Docker to VPS (ИМЯ)` для каждого сервера и проверяет панель снаружи. ПК и загрузка артефакта на сервер при обычных обновлениях не нужны. Сам по себе зелёный `verify` ещё не означает установленный релиз.
4. Удалённый браузер запускается и останавливается кнопками панели после входа администратора с 2FA. Отдельное окно ввода логина и пароля не требуется. Сеанс noVNC работает с заметной задержкой; после использования остановите его.

Команды диагностики ниже выполняются в SSH-окне VPS; проверка со своего компьютера помечена явно и тоже идёт в bash. Состояние ошибок и оставшиеся задачи см. в [истории](troubleshooting.md) и [roadmap](roadmap.md).

## Выдать доступ другому человеку и посмотреть его трафик

В разделе **Устройства** создайте отдельный профиль с понятным именем, например «Иван · Android», затем в **Обзоре** нажмите «Проверить» и «Применить конфигурацию». После совпадения ревизий откройте профиль этого устройства и передайте человеку VLESS URI или покажите QR-код. Он импортирует его в совместимый клиент с VLESS + REALITY + Vision. **Логин администратора, пароль, код 2FA и доступ к панели передавать не нужно.** Для второго телефона того же человека лучше создать ещё один профиль: тогда каждый можно отозвать отдельно.

Чтобы убрать старое устройство из списка, сначала нажмите «Отозвать», затем «Применить конфигурацию» и дождитесь равных ревизий. После этого у отозванного устройства появится доступное действие «Удалить» с подтверждением. Оно удаляет запись и текущий зашифрованный секрет профиля из таблицы устройств, но оставляет UUID и события в неизменяемом журнале. Удаление активного устройства или устройства с ещё не применённым отзывом API отклоняет; само удаление не требует нового применения Xray.

Раздел **Устройства** показывает отправленные и полученные байты по каждому активному профилю. Это данные Xray **с последнего запуска**; применение конфигурации и перезапуск Xray обнуляют счётчики. Они показывают объём трафика, но пока не подсчитывают число подключений, уникальные устройства или CPU конкретного человека. Один URI можно скопировать и использовать на нескольких устройствах, поэтому для достоверного учёта выдавайте отдельную ссылку каждому устройству и не пересылайте её посторонним. Для общего CPU, памяти и сетевой нагрузки сервера используйте на VPS `sudo docker stats --no-stream private-gateway-xray-1 private-gateway-edge-1`. Чтобы отключить доступ, нажмите «Отозвать» и снова примените конфигурацию. Отозванная ссылка перестанет создавать новые соединения; уже установленные соединения перепроверьте отключением клиента.

## Новый сервер

Каждый сервер — отдельная копия шлюза со своим доменом, панелью, устройствами и ключами. CI/CD обновляет все серверы из папки `deploy/servers` одной версией. Централизованного управления несколькими серверами из одной панели пока нет — это отдельный этап [roadmap](roadmap.md).

1. Возьмите VPS с Ubuntu 26.04 amd64, у которого есть вход по SSH для пользователя с правом `sudo` (обычно его создаёт провайдер). В панели провайдера разрешите входящие TCP 22, 80, 443 и 8443.
2. Создайте для сервера **собственный** домен, например в DuckDNS, с A-записью на IPv4 сервера.
3. **В Git Bash в основной папке проекта** (не в рабочей папке агента) выполните:

   ```bash
   bash scripts/add-server.sh ИМЯ IP_СЕРВЕРА ДОМЕН SSH_ПОЛЬЗОВАТЕЛЬ
   ```

   `ИМЯ` — латиница в нижнем регистре, цифры и дефис, например `vps-2`. Если SSH не на порту 22, добавьте порт пятым аргументом. Скрипт проверит, что домен указывает на сервер, и покажет отпечаток SSH-ключа сервера. Сравните его с отпечатком в консоли провайдера или с выводом `sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` в веб-консоли сервера и только тогда введите `yes`. Дальше скрипт по SSH подготовит ограниченный приёмник выкладки (пароль `sudo` вводится на сервере), запишет `deploy/servers/ИМЯ.conf` и сделает коммит в `master`. На вопрос о push ответьте `yes` или попросите агента отправить коммит позже. Ожидаемые строки: `VPS is ready to receive the first Docker release from GitHub Actions.` и `Server ИМЯ is prepared and deploy/servers/ИМЯ.conf is committed to master.`
4. В **GitHub → Actions → CI/CD** дождитесь зелёного `Deploy Docker to VPS (ИМЯ)`. Первая установка длится несколько минут: Docker загружает образы и собирает браузер. Успех отмечен строками `First Docker deployment verified: <SHA>` и `Panel https://ДОМЕН/ is ready with a trusted certificate.`
5. Выполните шаги [первого входа](#первый-вход-после-установки) на новом сервере.

Скрипт не трогает работающие серверы и не переносит их базу или ключи; новых GitHub Secrets не нужно. Чтобы перестать обновлять сервер, удалите его файл из `deploy/servers` и отправьте коммит: сам сервер продолжит работать с последней установленной версией. Текущий VPS был подготовлен до появления `add-server.sh` теми же `bootstrap.sh` и `bootstrap-receiver.sh`, но вручную; повторять подготовку на нём не нужно.

## Первый вход после установки

1. [Задайте логин и пароль администратора через SSH](#учётная-запись-администратора), затем откройте панель сервера, например `https://rb-gateway-3708079.duckdns.org/`: после пароля подключите приложение-аутентификатор через QR на странице и подтвердите шестизначный код. Проверьте «API подключён», «База данных подключена», «Xray настроен» и равенство применённой и новой ревизий. Публичная страница всегда показывает обычную форму входа; команд и состояния первоначальной настройки на ней нет. До создания учётной записи вход не откроется.
2. Создайте новое устройство, нажмите «Проверить» и «Применить конфигурацию», откройте «Устройства → Профиль». В совместимом клиенте импортируйте VLESS URI из буфера или отсканируйте QR-код; для sing-box/Mihomo доступны собственные форматы файлов. Порядок импорта приведён в [инструкции](clients.md). `127.0.0.1` в сообщении об импорте на iPhone относится к самому iPhone, не к серверу. Проверьте подключение с мобильного интернета и открытие HTTPS-сайта. Один успешный TCP-тест порта 443 не доказывает, что VLESS работает. При отзыве профиля проверьте совпадение применённой и новой ревизий: до этого момента старый профиль может продолжать работать. Если панель открыта через этот же VPN, его перезапуск может оборвать ответ браузеру; после восстановления связи обновите статус, прежде чем повторять действие. При одинаковых ревизиях повторное применение не нужно: оно ничего не меняет и не перезапускает Xray.
3. После входа по логину, паролю и коду 2FA нажмите «Запустить браузер» и «Открыть». Дополнительный логин и пароль не запрашиваются: доступ noVNC использует подтверждённый сеанс администратора. Без этого сеанса прямая ссылка возвращает 403. После завершения нажмите «Остановить браузер». Данные сессии находятся в tmpfs и стираются при остановке.

## Ключ выкладки и список серверов

GitHub Actions доставляет релиз по SSH под ограниченной учётной записью `gateway-deploy`: она может только передать проверенный архив обработчику обновлений. Нужен один GitHub Secret (**Settings → Secrets and variables → Actions**):

| Имя | Значение |
| --- | --- |
| `DEPLOY_SSH_KEY` | Полное содержимое закрытого ключа Windows `$HOME\.ssh\private-gateway-actions`. Вставляйте его только в поле GitHub Secret, не в переписку и не в репозиторий. Ключ должен работать без пароля. |

Открытая половина этого ключа лежит в `deploy/servers/deploy-key.pub`, её разрешает каждый сервер. Адрес, порт SSH, учётная запись, домен и ключ хоста каждого сервера записаны в `deploy/servers/ИМЯ.conf`. Это открытые данные, поэтому прежние секреты `DEPLOY_HOST`, `DEPLOY_PORT`, `DEPLOY_USER` и `DEPLOY_KNOWN_HOSTS` больше не нужны; 2026-10-17 они удалены из GitHub. Ключ хоста из записи сверяется при каждом подключении. Если сервер переустановлен и его ключ сменился, выкладка на него остановится, пока запись не обновят после сверки отпечатка.

`GATEWAY_API_TOKEN`, ключи REALITY, пароль PostgreSQL и другие секреты приложения остаются на каждом сервере в `/etc/private-gateway-docker/stack.env`. `.env` на вашем ПК GitHub Actions не читает. `verify` — CI: те же проверки в Docker, что `bash scripts/dev.sh test` на ПК, затем сборка релиза и production-образов и тест `scripts/test-install-update.sh`. Он ставит стек на чистый runner с Ubuntu 26.04 настоящими `bootstrap.sh`, приёмником и `install.sh`, обновляет его через `update.sh` (обновление одной панели должно пересоздать только контейнер api, а postgres, Xray, браузер, Caddy и HAProxy оставить работать) и проверяет откат после двух обновлений: одно ломает панель, другое — VLESS-трафик. Прежняя версия, конфигурация HAProxy, устройство и VLESS-трафик должны вернуться. Эти шаги идут при push любой ветки, так что ветку можно проверить на GitHub до `master`; релиз загружается и выкладывается только из `master`. `Deploy Docker to VPS (ИМЯ)` — CD для одного сервера: доставка, установка проверенного релиза и внешняя проверка панели. Сбой на одном сервере не останавливает выкладку на остальные.

Для проверки откройте **Actions → CI/CD** после следующего коммита в `master` или выполните в терминале bash `gh run list --branch master`, если установлен GitHub CLI. Сначала завершится `verify`, затем `Deploy Docker to VPS (ИМЯ)` для каждого сервера. Успешная выкладка выводит `Docker deployment verified: <SHA>` и `Panel https://ДОМЕН/ is ready with a trusted certificate.`; внешняя проверка подтверждает панель, но не VLESS-профиль. До этого `update.sh` на сервере проверяет настоящий VLESS-трафик через порт 443 профилем первого активного устройства (`vpn-smoke.py`, до трёх попыток, в журнале — `VLESS traffic OK`). Если трафик не проходит, выкладка откатывается, а проверка повторяется на прежнем релизе. Без активных устройств проверка пропускается. Профиль для неё выдаётся внутри сервера, поэтому каждая выкладка добавляет в журнал действий событие «Профиль выдан». Это серверная проверка, а не проверка приложения на устройстве. На VPS можно сравнить `sudo cat /etc/private-gateway-docker/installed.version` с SHA коммита и проверить `sudo docker compose --env-file /etc/private-gateway-docker/stack.env -f /opt/private-gateway-docker/current/docker/compose.yml ps`. Новый релиз сохраняет существующие устройства, базу и ключи Docker. Перед миграцией создаётся дамп PostgreSQL и копия env, Caddyfile, `haproxy.cfg` и конфигурации Xray в `/var/backups/private-gateway/`. При ошибке выполняется откат: возвращаются база из дампа, эти файлы, прежний релиз и его контейнеры, включая HAProxy на порту 443. Если откат тоже завершился ошибкой, не повторяйте запуск без проверки этого backup и состояния контейнеров.

Что прерывается при обновлении:

- API останавливается на время дампа и миграций (при выкладке `5184b79` — около 15 секунд); панель в это время недоступна.
- Контейнеры api, browser и xray пересоздаются, только если изменился их образ. Тег образа — хеш его Dockerfile и копируемых в образ файлов (`docker/image-tags.py`): изменение панели или API пересоздаёт только api, новый `bin/xray` — api и xray. Пересоздание xray рвёт VPN-подключения на несколько секунд, пересоздание browser закрывает открытый удалённый браузер. Две первые выкладки после перехода на такие теги ещё пересоздают все три контейнера: первую выполняет прежний `update.sh`, вторая меняет теги с SHA коммита на хеш содержимого.
- Caddy и HAProxy пересоздаются, только если изменилась их конфигурация. HAProxy держит все VPN-подключения, поэтому коммит с изменением `haproxy.cfg.template` обрывает их на время перезапуска.
- Образы postgres, caddy и haproxy закреплены по digest в `deploy/docker/compose.yml` и меняются только коммитом. Коммит с новым digest пересоздаёт свой контейнер при выкладке; для haproxy это разрыв VPN-подключений. Первая выкладка с закреплёнными digest один раз пересоздаёт все три контейнера.

## Учётная запись администратора

После зелёного `verify` и `Deploy Docker to VPS` с версией, содержащей браузерную настройку 2FA, выполните **в SSH-терминале на сервере** (на текущем VPS приглашение начинается с `romanburov@vps3708079`):

```bash
sudo python3 /opt/private-gateway-docker/current/docker/admin-credentials.py
```

Команда спросит логин (3–64 латинские буквы, цифры, точка, дефис или подчёркивание; также можно использовать адрес электронной почты длиной до 64 символов) и новый пароль (минимум 14 символов) дважды. Пароль при вводе не отображается. **Секрет 2FA в терминале больше не показывается.** После сообщения об успешной записи откройте панель в браузере. Введите логин и пароль, затем отсканируйте показанный на странице QR-код приложением Google Authenticator, Microsoft Authenticator или 2FAS. Если сканирование невозможно, введите показанный **на этой странице** ключ вручную. Введите шестизначный код из приложения в браузере; только тогда 2FA включится и откроется панель. Для кодов важно правильное время на телефоне и VPS.

Скрипт сохраняет закрытые копии базы и прежнего `stack.env` в `/var/backups/private-gateway/`, записывает логин и хеш пароля в PostgreSQL, удаляет старые поля администратора из рабочего env-файла, перезапускает только API и проверяет первый этап входа через HTTPS. При сбое возвращает прежние настройки; сообщение укажет backup. Незавершённый QR действует только пять минут и хранится в памяти API. После подтверждения кода секрет 2FA хранится в PostgreSQL зашифрованным с помощью серверного `GATEWAY_MASTER_KEY`; пароль в открытом виде и URI не сохраняются. Действующие VLESS-устройства и REALITY-ключи не меняются. Чтобы сменить логин или пароль, повторите команду через SSH с `sudo`: старые сеансы и прежний 2FA-секрет станут недействительными, после чего снова подключите аутентификатор в браузере.

Если до обновления в env уже был логин и пароль прежнего формата, новый API временно переносит их в PostgreSQL **без старого TOTP-секрета**. После обновления всё равно выполните команду выше: задайте новый пароль, удалите прежние поля из рабочего env-файла и подключите новый аутентификатор в браузере. Старый секрет был опубликован в переписке и не должен использоваться. Если прежняя терминальная команда не завершилась, записи для переноса нет; новая команда создаст её. Никому не отправляйте QR, ключ, пароль или код. Публичный API принимает только временный сеанс, выданный после пароля и 2FA; сессия живёт не более восьми часов и пропадает при перезапуске API. `GATEWAY_API_TOKEN` остаётся только для `gatewayctl` **внутри API-контейнера**. Его ротация выполняется `rotate-admin-token.py` и не меняет логин, пароль или TOTP.

## Проверка и диагностика

Без SSH сервер проверяет себя из панели: раздел «Проверка» → «Проверить». Он показывает состояние PostgreSQL, применённой конфигурации и процесса Xray, сайта маскировки REALITY и сертификата панели и отправляет настоящий VLESS-запрос через Xray сервера ([подробнее](privacy-checks.md#раздел-проверка-в-панели)). Для этого API обращается к Xray и Caddy по внутренним сетям Docker: `GATEWAY_XRAY_SERVER_ADDRESS=xray:443`, `GATEWAY_PANEL_TLS_ADDRESS=caddy:443` и `GATEWAY_PANEL_DOMAIN` задаёт `compose.yml`, менять их не нужно.

Эти команды не выводят URI устройств:

```bash
sudo docker compose --env-file /etc/private-gateway-docker/stack.env \
  -f /opt/private-gateway-docker/current/docker/compose.yml ps
sudo docker compose --env-file /etc/private-gateway-docker/stack.env \
  -f /opt/private-gateway-docker/current/docker/compose.yml logs --tail=100 api xray browser caddy edge
curl --noproxy '*' -fsS \
  --resolve rb-gateway-3708079.duckdns.org:443:127.0.0.1 \
  https://rb-gateway-3708079.duckdns.org/readyz
sudo ss -lntp | grep -E ':(22|80|443|8443)[[:space:]]'
```

Если совместимый клиент показывает тайм-аут, а порт 443 отвечает, проверьте настоящий VLESS-трафик на VPS:

```bash
sudo python3 /opt/private-gateway-docker/current/docker/vpn-smoke.py
```

Проверка берёт один активный профиль через внутренний API, сверяет его с загруженной конфигурацией Xray, запускает временный локальный Xray-клиент и делает HTTPS-запрос через VLESS. URI, UUID и ключи не выводятся; временный конфиг клиента удаляется после проверки. При сбое команда показывает этап: сверка профиля, соединение VLESS, TLS или ответ сайта. `VLESS traffic OK` подтверждает работоспособность профиля и Xray **на сервере**; подключение из сети телефона нужно проверить отдельно.

Если проверка обрывается на `HTTPS handshake through VLESS`, запустите дополнительную изолированную проверку:

```bash
sudo python3 /opt/private-gateway-docker/current/docker/vpn-smoke.py --isolated
```

Она сверяет публичный ключ профиля с закрытым ключом Xray через OpenSSL, затем временно запускает вторую копию Xray на локальном порту с той же конфигурацией и удаляет временные файлы. Работающий контейнер не меняется. Если изолированная проверка проходит, ищите причину в сетевом пути Docker или окружении контейнера. Если она падает, строка `isolated Xray` покажет тип отказа без вывода UUID и ключей.

При прежней ошибке `REALITY rejected: handshake did not complete successfully` временная проверка с `--isolated-target www.cloudflare.com` прошла, в отличие от `www.microsoft.com`. На текущем VPS рабочие target и SNI **уже заменены** на `www.cloudflare.com`, а обычный `vpn-smoke.py` после этого прошёл. Новые Docker-установки также используют Cloudflare по умолчанию.

Только при переносе другой **старой** Docker-установки, где в `stack.env` ещё указан `www.microsoft.com`, одноразовая миграция выполняется командой:

```bash
sudo python3 /opt/private-gateway-docker/current/docker/change-reality-target.py
```

Скрипт сохраняет закрытую копию `stack.env` и Xray-конфигурации в `/var/backups/private-gateway/`, меняет target и SNI, применяет конфигурацию и проверяет VLESS-трафик. На текущем VPS он уже вернул `VLESS traffic OK: TLSv1.3; target www.cloudflare.com; backup ...`; повторять его для обычных обновлений не нужно. При ошибке `repair and rollback failed` проверьте backup и контейнеры до нового запуска.

После любой смены target откройте **Устройства → Профиль** для активного устройства и импортируйте обновлённый URI или QR в совместимый клиент. Старый URI с `sni=www.microsoft.com` не подходит. Для проверки подключения откройте `https://api.ipify.org/`; он показывает только исходящий IP, и на текущем VPS ожидается `162.35.172.6`. Внешняя проверка с iPhone по LTE уже выполнена; Windows с новым профилем пока не проверен.

Если внутренний CLI-токен будет раскрыт, выполните **на VPS**:

```bash
sudo python3 /opt/private-gateway-docker/current/docker/rotate-admin-token.py
```

Команда создаёт новый случайный токен только для внутреннего CLI, проверяет, что он не открывает публичный API и что noVNC недоступен без входа администратора, и откатывает настройки при сбое. Логин, пароль, TOTP, устройства, база и REALITY-ключи сохраняются. Токен на текущем VPS **уже ротирован** после раскрытия прежнего; без новой причины повторять команду не нужно. Новый токен хранится в `/etc/private-gateway-docker/stack.env`; скрипт **не печатает** его. Для входа в noVNC этот токен не нужен. Профиль устройства и QR открывайте только после входа администратора в панель. QR формируется в браузере без внешнего сервиса; он содержит секрет устройства, поэтому закрывайте окно после импорта.

Со своего компьютера (bash: Git Bash на Windows, терминал на macOS и Linux) одной командой проверьте DNS, TCP 443 и настоящий HTTPS с проверкой сертификата:

```bash
curl --noproxy '*' --silent --show-error --output /dev/null \
  --write-out 'ip=%{remote_ip} http=%{http_code} tls=%{ssl_verify_result}\n' \
  https://rb-gateway-3708079.duckdns.org/
```

Ожидается `ip=162.35.172.6 http=200 tls=0`: адрес из DNS, открытый порт и доверенный сертификат. Это подтверждает панель, но не клиентский VLESS-трафик. Если клиент всё ещё не работает, сравните URI с новым профилем, проверьте применённую ревизию, журналы Xray **на сервере**, попытку с другой мобильной сети и время устройства. Не публикуйте URI, UUID доступа, ключи или полные журналы без очистки.

## Хранение, откат и удаление старого стека

Файл `/etc/private-gateway-docker/stack.env` с правами `0600` содержит секреты. PostgreSQL находится в Docker volume `private-gateway_postgres-data`, состояние Xray — в `/var/lib/private-gateway-docker/xray`, сертификаты Caddy — в Docker volume `private-gateway_caddy-data`. Для восстановления нужны согласованные копии базы и env-файла; один дамп базы не позволит расшифровать профили. Делайте внешнюю зашифрованную копию и проверяйте восстановление отдельно. `docker compose down --volumes` удаляет новую базу и сертификаты; не используйте эту команду для обычной остановки. Для перезапуска сервера достаточно `sudo reboot`, контейнеры используют `restart: unless-stopped`.

Старые systemd-службы, Podman worker, host PostgreSQL и старые папки релизов отключены, но их файлы оставлены как точка возврата. Внешние копии и очистку старой установки владелец решил не проводить (см. [решения владельца](roadmap.md#решения-владельца)); удалять эти файлы без нового решения не нужно. Не запускайте старые и новые Xray/HAProxy/Caddy одновременно на портах 443/8443.
