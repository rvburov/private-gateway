# История ошибок и диагностика

## Дополнительный вход XHTTP — 2026-10-31

- Если в окне профиля нет XHTTP, проверьте, что установлен релиз с этой функцией и
  она включена на VPS. Настройка выключена по умолчанию; отсутствующий вариант не
  заменяется демонстрационной ссылкой.
- Если в публичной подписке пока только TCP, убедитесь, что текущая ревизия
  успешно применена. До этого XHTTP не рекламируется. Hiddify, sing-box и Mihomo
  намеренно сохраняют совместимую выдачу TCP; неизвестные старые клиенты могут
  не импортировать смешанный список и требуют отдельного TCP URI/QR.
- Успешный серверный XHTTP smoke не доказывает доступность нового порта из сети
  телефона. Отдельно проверьте разрешение TCP-порта в брандмауэре и панели хостинга,
  приложение, версию ядра и импорт VLESS + XHTTP + REALITY. Flow Vision для этого
  транспорта не задают.
- «Не измерено» в окне профиля означает отсутствие измерения задержки для этого
  варианта. Открытый TCP-порт и `xray run -test` не измеряют скорость и не заменяют
  реальный запрос через клиент. Повторный запуск ядра на каждый запрос уничтожает
  прогрев XMUX; методика сравнения находится в [руководстве XHTTP](xhttp.md).
- В реализации выключенный XHTTP не резервирует host-порт: публикация находится
  только в условном `compose.xhttp.yml`. При диагностике проверяйте итоговую
  конфигурацию без вывода её секретных значений в терминал или переписку.
- Если CI-тест установки завершился только `exit 1`, смотрите аннотации задания:
  `phase` указывает этап сценария, а `stage` — шаг настройки XHTTP. При откате
  дополнительно выводятся его результат и стадия ошибки восстановления. Аннотации
  содержат фиксированные категории и номер строки, без команд, ключей и профилей.
  Локальный `scripts/dev.sh test` проверяет эти обработчики отдельно и не запускает
  установку в `/etc`, `/opt` и `/var`: полный сценарий выполняется только на runner CI.
- В CI №104 настройка XHTTP прошла проверки VPN, но последующая проверка панели
  завершилась ошибкой. Настройщик проверял API внутри контейнера и оба транспорта,
  а внешний путь HTTPS → HAProxy → Caddy → API не был условием успеха. Теперь он
  ожидает готовности канонической HTTPS-панели с проверкой TLS и ограничением
  60 секунд; постоянный отказ запускает откат. После отката проверяется и панель.
  Аннотация `panel-ready` сообщает только числовой HTTP-статус и код завершения
  curl; адрес, тело ответа и сырой stderr не публикуются.
  Причина недоступности панели по доступному журналу не установлена;
  перезапуск Caddy или ослабление проверок TLS не применяются.

Здесь записаны существенные ошибки, которые встретились при запуске текущего VPS. Состояние ниже относится к установке Docker на `162.35.172.6` с доменом `rb-gateway-3708079.duckdns.org`. Команды для обычной эксплуатации находятся в [инструкции по развёртыванию](deployment.md), планы — в [roadmap](roadmap.md). Секретные токены, ключи и VLESS URI здесь намеренно не приводятся.

## Нечитаемый русский текст в скачанном отчёте — 2026-10-23

Владелец прислал серверный JSON, где «База данных» выглядела как `Р‘Р°Р·Р° РґР°РЅРЅС‹С…`; так же были искажены сообщения замеров и описания нагрузки. Этот фрагмент точно получается при чтении байтов UTF-8 как Windows-1251. Конкретная программа, в которой открылся файл, не установлена. В проверенных исходниках русский текст корректен, ответы API уже указывают `application/json; charset=utf-8`; сам скачиваемый Blob ранее не указывал кодировку. После сохранения файла редактор также может потерять MIME-метаданные и выбрать свою кодировку.

Сначала были добавлены русский TXT в UTF-8 с BOM и промежуточный JSON с Unicode-символами в виде ASCII-последовательностей `\uXXXX`. Теперь в панели оставлена одна кнопка «Скачать отчёт»: она сохраняет только читаемый русский TXT. API и результаты в интерфейсе не перекодируются эвристиками.

Скачайте отчёт заново этой кнопкой. Старый исходный JSON можно открыть с явным выбором UTF-8 в редакторе. Если его уже сохранили после неправильного декодирования, одного переключения кодировки может быть недостаточно. Открытие нового TXT на Windows и iPhone владельца нужно подтвердить отдельно; локальная проверка байтов и тесты программы не заменяют эту проверку.

## Вход, связь и ошибки API — 2026-10-23

Эти состояния имеют разные причины. Ошибка связи с панелью сама по себе не доказывает, что VPS выключен или VPN перестал передавать трафик.

| Статус | Что произошло | Что сделать |
| --- | --- | --- |
| «Нужен вход» | Сервер ответил HTTP 401: сеанс не принят. По этому ответу нельзя отличить истёкший вход от отозванного. | Нажать «Войти снова» и пройти вход. |
| «Нет сети» | Браузер сообщает, что устройство отключено от сети. | Восстановить подключение и проверить связь снова. |
| «Нет связи» | Браузер не получил полный ответ: возможен сетевой сбой, ошибка DNS или TLS. | Проверить сеть, VPN и адрес панели; повторить проверку связи. |
| «Нет ответа» | Время ожидания ответа истекло. | Повторить чтение состояния; ранее отправленное изменение могло примениться. |
| «Ошибка API» | Сервер ответил ошибкой HTTP; панель сохраняет её код. | Прочитать код и пояснение: например, при ограничении частоты подождать, при ошибке службы повторить проверку позже. |
| «Неверный ответ» | Ответ получен, но панель не смогла прочитать его формат. | Обновить страницу; если ошибка повторяется, сохранить её текст для диагностики. |

Кнопка «Войти снова» открывает вход и очищает локальный сеанс панели. Она не вызывает выход на сервере и не отзывает сохранённый вход или push. Кнопка «Выйти» делает это намеренно; обычный сетевой сбой сохранённый вход не удаляет.

Проверка связи заново читает данные, не повторяет добавление или отзыв устройства и применение конфигурации. Если ответ на изменение потерялся, сначала обновите состояние и проверьте результат. После успешного чтения статус связи восстанавливается. «API подключён» подтверждает связь с API; работу Xray и передачу VPN проверяют отдельно в разделе «Сервер» и на устройстве.

## Кнопки и нижний отступ на iPhone — 2026-10-23

Часть действий выглядела как обычный текст, а последние элементы страницы могли попадать под нижнее меню. Прежний отступ снизу составлял 116 пикселей и не учитывал фактическую высоту меню с безопасной областью экрана и увеличенным текстом. В расчётном примере с нижней безопасной областью 34 пикселя меню вырастало до 130 пикселей — больше отступа на 14 пикселей.

Теперь панель измеряет высоту нижнего меню и оставляет под содержимым эту высоту плюс 40 пикселей. Отступ для прокрутки использует то же значение; запасной расчёт также учитывает безопасную область экрана. Обычные действия на телефоне оформлены кнопками на всю строку. Навигация, выбор темы, «?», закрытие и короткие переключатели остаются компактными. У списков выбора отделена стрелка, у раскрывающихся разделов сохранено обычное поведение браузера.

После выкладки нужно проверить на настоящем iPhone в Safari и установленной панели: последние карточки полностью прокручиваются выше меню, кнопки доступны, подписи списков и раскрывающихся разделов не обрезаются. Повторить с увеличенным текстом и после поворота экрана. Проверки макета в Chromium не заменяют Safari и устройство владельца.

## IP2Location: нет данных или отметка дата-центра — 2026-10-23

Справка IP2Location не измеряет скорость и не устанавливает факт утечки. `DCH` — тип использования дата-центром, обычный для VPS; `T1` — категория в базе, а не результат теста скорости. Геолокация и признаки прокси приблизительны. `null` или «Нет данных» не равны отрицательному результату проверки.

| Состояние | Что проверить |
| --- | --- |
| Источник не настроен (`not_configured`) | На VPS не задан необязательный ключ; настройте его через SSH по [инструкции](deployment.md#ip2location). Остальные функции панели доступны. |
| Частичные данные (`partial`) | Часть полей не предоставлена. Сверьте возможности и лицензию своего тарифа; не считайте пустые признаки значением «нет». |
| Источник недоступен (`unavailable`) | Возможны отказ сервиса, неверный ключ, сетевой сбой или непригодный ответ. Повторите позже и проверьте настройку на VPS, не публикуя ключ и URL запроса. |
| Предел запросов (`rate_limited`) | Подождите; действуют ограничения приложения и провайдера. Частое повторение не расширяет тариф. |
| Введён неверный IP | Используйте публичный IPv4 или IPv6, без URL, порта и имени сайта. |

Ручной поиск другого IP не подтверждает маршрут вашего браузера или сервера. В «Проверке» используется измеренный адрес браузера, а в «Сервере» — результат успешного VLESS-запроса. Если он не получен, адрес настройки узла не заменяет проверку.

Полные поля, реальный запрос с ключом и доступность production API без ключа ещё не подтверждены на VPS; локальные тестовые ответы не считаются такой проверкой. Стоимость определяется условиями вашего аккаунта IP2Location.io.

## DNS, домен и порты

Текущая схема после перехода на основной вход: панель и новые профили используют
8443; внешний 443 сохранён в HAProxy для совместимости. Исторические записи ниже
о перенаправлении 8443 на 443 и выборе резервного профиля описывают прежние выпуски.
Актуальный порядок — в [развёртывании](deployment.md#основной-внешний-вход-8443-с-сохранением-443).

### Тайм-аут 443 при доступном 8443 — 2026-10-20

Владелец проверил несколько сетей: без другого VPN панель на 443 не открывалась,
с VPN открывалась; на том же IPv4 порт 80 возвращал 308, а 8443 — 301 на 443.
`curl --resolve` с закреплённым `162.35.172.6` также завершался тайм-аутом на 443.
Это исключает DNS как единственное объяснение. Замена имени TLS на другое тоже
не восстановила соединение. В предоставленном захвате часть соединений на 443
устанавливала TCP-соединение, после чего передача останавливалась. Точный узел,
причина фильтрации или сбой маршрута не установлены. Проверка с самого VPS
не подтверждает доступность из сети клиента.

Первым решением было сделать 8443 полноценным резервным входом панели и VLESS вместо
перенаправления на 443. Подготовлены изменения HAProxy/Compose, выдача профилей
и подписки для выбранного порта, сохранение порта noVNC и проверки обновления.
Первый переход требует подготовительного релиза установщика: при откате старый
установщик может попытаться запустить Caddy на 8443, пока новый HAProxy ещё
занимает этот порт. Порядок двух релизов описан в
[развёртывании](deployment.md#первый-переход-на-резервный-вход-8443).
После выкладки владелец открыл панель на 8443 без VPN и подтвердил подключение
Hiddify 4.1.1 на Windows: Chrome показал IP шлюза `162.35.172.6`. Это подтверждение
Windows в использованной сети; имя профиля «iPhone» не доказывает проверку телефона.
Мобильная сеть с новой схемой остаётся отдельной проверкой.

Следующим решением владельца основной адрес панели и все выдаваемые профили
переведены на 8443 без выбора порта, а 443 сохранён для совместимости. Это обход
наблюдавшейся недоступности, а не установленная причина сбоя 443. Старые действительные
ссылки на 8443 сохраняются; `port=primary` теперь означает текущий основной профиль.
Подписку с недоступным адресом на 443 нужно однократно переимпортировать.

### Предыдущие случаи

На VPS полный прогон остановился при сборке образа проверок с `Unsupported architecture:`
без значения. Docker использовал старый сборщик без Buildx и не заполнил `TARGETARCH`.
В `scripts/dev.sh` архитектура теперь читается через `docker version` и передаётся
явным `--build-arg`; установка системного плагина для этого не нужна.

| Симптом | Что выяснили | Итог |
| --- | --- | --- |
| `rb-gateway-3708079.mooo.com` отвечал `NXDOMAIN` через 1.1.1.1, 8.8.8.8 и авторитетные `ns1`–`ns4.afraid.org` | Запись FreeDNS не появилась в опубликованной зоне; добавление адреса в код приложения не могло исправить DNS. | Создан `rb-gateway-3708079.duckdns.org`. Публичный DNS вернул `162.35.172.6`. |
| Исторический переход к адресу без порта | Xray занимал внешний порт 443, а Caddy слушал отдельно 8443. | На этом этапе HAProxy на 443 направлял SNI панели в Caddy, остальные соединения — в Xray, а 8443 перенаправлял на адрес без порта. Теперь основной адрес снова с `:8443`, оба TLS-входа принадлежат HAProxy. Имя с окончанием `.duckdns.org.com` этому домену не принадлежит. |
| TCP 443 отвечал, а клиент VPN показывал тайм-аут | Доступный порт и TLS fallback REALITY подтверждают только сетевой вход, а не успешную авторизацию VLESS. | Для проверки профиля добавлен `docker/vpn-smoke.py`; после исправления target он вернул `VLESS traffic OK: TLSv1.3`. |

## Hiddify на Windows и оценка DNS

На проверенном ПК Hiddify 4.1.1 с Chrome по Wi-Fi работал в режиме «Системный прокси»: сайты видели IPv4 шлюза `162.35.172.6`. После переключения на режим «VPN» появился домашний IP. Причина работы TUN не установлена; до диагностики верните системный прокси и проверьте внешний IP. Не считайте надпись «Подключено» доказательством маршрутизации.

Панель ранее помечала DNS как «Проблема», если найденный резолвер принадлежал ASN, отличному от ASN шлюза, и не входил в короткий список публичных DNS. В тестах пользователя встречались HostPapa, Clouvider и WoodyNet наряду с Interserver, Google и Cloudflare, но домашний провайдер в предоставленных результатах не появлялся. Разный ASN резолвера не доказывает, что запрос ушёл мимо прокси. Такой результат теперь показывается как «Внимание» с предложением отдельно проверить маршрут DNS, если распознан домашний провайдер.

В обычном Chrome WebRTC ранее был выключен, но в инкогнито при том же IPv4 шлюза панель увидела российский адрес через WebRTC. Chrome обычно отключает расширения в инкогнито; на ПК установлены ZeroOmega и WebRTC Control, но не подтверждено, какой из них работал в этом окне. Для диагностики в `chrome://extensions` откройте «Сведения» нужного доверенного расширения, проверьте разрешение работы в инкогнито, затем в новом окне инкогнито повторите внешний IP и WebRTC-тест. Если адрес домашнего провайдера виден, не используйте это окно для приватного просмотра. Переключение Hiddify в TUN уже показывало домашний IP и не является проверенным исправлением.

## Отзыв устройства и применение конфигурации

После отзыва устройства панель может показывать «Применённая / новая версия: 5 / 6», а при нажатии «Применить конфигурацию» — ошибку связи с API. Пока версии различаются, старый профиль может оставаться в Xray. Возможная причина: владелец открыл панель через тот же VPN, который перезапускается при применении; разрыв HTTP-запроса раньше отменял серверную транзакцию. Теперь после авторизации сервер завершает применение и запись ревизии, даже если браузер потеряет соединение. Проверка на PostgreSQL с принудительным разрывом клиента это воспроизводит; на рабочем VPS результат ещё нужно подтвердить.

Если ошибка появилась на текущем VPS, отключите VPN на устройстве администратора и обновите панель. При повторной ошибке выполните в SSH на VPS `sudo docker exec private-gateway-api-1 /usr/local/bin/gatewayctl config validate`, затем `sudo docker exec private-gateway-api-1 /usr/local/bin/gatewayctl config apply` и проверьте `sudo docker exec private-gateway-api-1 /usr/local/bin/gatewayctl status`. Секреты эти команды не печатают. Считайте отзыв завершённым только при равных `APPLIED REVISION` и `DESIRED REVISION`. Владелец подтвердил `6 / 6` после выпуска `bdb9c22`, но при повторном нажатии «Применить» увидел ошибку связи: прежняя реализация повторно перезапускала Xray даже без изменений. Теперь сервер считает применение актуальной ревизии завершённым без перезапуска, панель отключает ненужную кнопку и скрывает устаревшую ошибку после подтверждения одинаковых версий. Владелец подтвердил неактивную кнопку и отсутствие ошибки после выпуска `33bb494`.

Ранее отозванные устройства продолжали накапливаться в разделе «Устройства»: в интерфейсе было только «Отозвать», а внешний ключ неизменяемого журнала не позволял удалить строку устройства. Теперь после применения отзыва можно удалить устройство с подтверждением. Из таблицы устройств исчезают запись и зашифрованный секрет, а журнал сохраняет UUID и действия без внешнего ключа на удалённую строку. До равенства ревизий удаление запрещено, чтобы старый профиль не остался в работающей конфигурации Xray без записи в базе. Для выпуска `eac27e1` владелец подтвердил зелёный CI/CD и успешное удаление отозванного устройства в панели VPS.

## Переход на Docker и автоматическое развёртывание

2026-10-17 при разборе `update.sh` найдены два дефекта отката и обновления. В журнале проекта откатов после перехода на общий порт 443 нет, так что на рабочем VPS они, по-видимому, не проявлялись.

- **Откат оставлял порт 443 закрытым.** При сбое обновления скрипт останавливал HAProxy и больше не запускал его, поэтому после любого отката панель и VPN не работали до ручного запуска. Остановка досталась от перехода на общий порт 443, когда в прежнем релизе HAProxy ещё не было.
- **Новый `haproxy.cfg` не доходил до HAProxy.** Файл заменялся новым, а контейнер, смонтировавший его при запуске, продолжал видеть прежнее содержимое. Изменение маршрутизации порта 443 вступило бы в силу только после случайного пересоздания контейнера. Шаблон с момента появления не менялся, так что на сервере действует правильная конфигурация.

Теперь откат возвращает прежние контейнеры вместе с HAProxy. Caddy и HAProxy пересоздаются только тогда, когда их файл действительно изменился, и при обновлении, и при откате; раньше Caddy пересоздавался при каждой выкладке. Оба случая проверяет в CI `scripts/test-install-update.sh`: релиз, который направляет имя панели в Xray, должен откатиться, а панель, устройство и VLESS-трафик — вернуться.

Первый прогон этого теста остановился раньше, на проверке Caddyfile в установщике: `mkdir /data/caddy/pki: read-only file system`. Тест ставит панель на имя `.localhost`, а для таких имён (и `.internal`) Caddy при `caddy validate` создаёт собственный CA. Проверочный контейнер был запущен только для чтения. Публичного домена VPS это не касалось. Теперь проверка в `install.sh` и `update.sh` получает временный `/data` в tmpfs, поэтому установщик работает и с внутренним именем панели.

Следующие прогоны доходили до первого `gatewayctl config apply` и получали HTTP 503 «Xray operation failed». API не записывал причину, поэтому теперь он пишет в свой журнал саму ошибку; ключ REALITY и UUID клиентов менеджер Xray убирает из неё заранее. Причина оказалась такой: `fork/exec /usr/local/bin/wait-xray.py: permission denied`. На runner GitHub с Ubuntu 26.04 контейнер API не запускал скрипт по его строке `#!/usr/bin/env python3`, хотя у файла права `0555`, а ELF-программу `xray` тот же контейнер запускал. В Docker Desktop такой запуск работает, и на рабочем VPS применение конфигурации тоже проходило; точную причину запрета на runner установить не удалось. Теперь API вызывает `/usr/local/bin/python3 /usr/local/bin/wait-xray.py` — так же, как контейнеры xray и browser запускают свои скрипты на Python. По той же причине browser worker запускает `start.sh` и `healthcheck.sh` через `/bin/sh`.

Позже тест однажды сообщил, что устройство не пережило откат, хотя база восстанавливалась так же, как в прошлом успешном прогоне. Проверка передавала вывод `gatewayctl status` из `docker compose exec` в `grep -q`. `grep -q` завершается на первом совпадении; если писатель ещё не закончил вывод, он получает SIGPIPE, и `set -o pipefail` превращает это в провал проверки. Результат зависел от того, как разбивался вывод. Тот же приём в `update.sh` определял, есть ли HAProxy в старом и новом стеке, а в `install.sh` — есть ли уже контейнеры проекта: SIGPIPE там читался бы как «нет». Теперь все три места сначала сохраняют вывод целиком, а тест при провале печатает состояние.

## VPN не работает через домашний Wi-Fi

Если панель и VPN работают через мобильную сеть, но не через Wi-Fi, выключите VPN и сравните оба подключения. В Bash на macOS, Linux или Windows (Git Bash) выполните:

```bash
host=rb-gateway-3708079.duckdns.org
ip=162.35.172.6
curl -4 -sS --noproxy '*' --connect-timeout 10 --max-time 15 -o /dev/null -w 'http=%{http_code}\n' "https://$host/"
curl -4 -sS --noproxy '*' --resolve "$host:443:$ip" --connect-timeout 10 --max-time 15 -o /dev/null -w 'http=%{http_code}\n' "https://$host/"
```

Ошибка `curl: (6)` у первого запроса при успешном втором указывает на DNS. Если оба запроса не работают лишь через Wi-Fi, проверьте WAN-адрес и журнал домашнего роутера, перезагрузите его и повторите тест. Для проверки внешнего адреса при выключенном VPN используйте `curl -4 -sS --noproxy '*' https://api.ipify.org`. Проброс портов на роутере для доступа к VPS не нужен.

После восстановления связи включите VPN через Wi-Fi и выполните `curl -4 -sS --max-time 20 https://api.ipify.org`: для текущего шлюза ожидается `162.35.172.6`.

В проверенном случае сбой затронул несколько устройств домашней сети, а мобильная сеть работала. На VPS входящие TCP SYN доходили, сервер отправлял SYN-ACK, но соединение не завершалось. После перезапуска TP-Link Archer AX12 и очистки таблицы NAT панель вернула HTTP 200, а VPN через Wi-Fi показал IP шлюза. Внешний IP роутера не изменился. Точное место потери пакетов не установлено; при повторении проверьте прошивку роутера и передайте провайдеру или хостингу время сбоя и сетевой захват.

## Вход в панель и доступ к браузеру

После установки форма входа говорила «Токен недействителен» и на Windows, и на iPhone. Проверки показали, что токен в `stack.env` совпадал с токеном API, а авторизованный HTTPS-запрос к API возвращал `200`. Точная причина отказа формы не была установлена. Старый токен был раскрыт в переписке, поэтому его ротировали; после этого пользователь успешно вошёл в панель. Новый токен хранится только на VPS в `/etc/private-gateway-docker/stack.env` и не записан в репозиторий.

Раньше Caddy открывал отдельное системное окно Basic Auth: логин `browser` и серверный `GATEWAY_API_TOKEN`. Поэтому владелец видел второй запрос пароля после входа в панель. Теперь это окно устранено: noVNC принимает только cookie, связанный с сеансом администратора после проверки пароля и TOTP. Запрос `/browser/vnc.html` без такого cookie возвращает `403`; при правильном cookie, но остановленном browser worker возможен `502`. Внутренний CLI-токен не открывает публичный API и noVNC. После выхода из панели, смены пароля или перезапуска API откройте браузер заново через панель.

Позже на странице входа вновь отображалось поле `GATEWAY_API_TOKEN` вместо логина и пароля. Причина: новая страница получала `configured: false` из `/api/v1/auth/config` и показывала оставленную запасную форму. После удаления этой формы на странице показывались внутренняя SSH-команда и состояние первоначальной настройки — их тоже убрали. Теперь публичная страница всегда показывает только обычный вход по логину и паролю, `/api/v1/auth/config` удалён, а до создания учётной записи попытка входа получает общий отказ. Публичный API не принимает CLI-токен. Если после зелёного CD всё ещё видна старая форма, сравните версию релиза на VPS с коммитом и обновите страницу браузера; сама отправка коммита не подтверждает успешное развёртывание.

## Удалённый браузер

Внутренний smoke test подтвердил HTTP, WebSocket и VNC. Удалённый Chromium через `2ip.io` и `https://api.ipify.org/` показал IPv4 VPS. `api.ipify.org` — API, поэтому страница с одной строкой IP ожидаема; полноценный сайт находится на `https://www.ipify.org/`. Если вместо сайта открылась поисковая выдача, вводите полный URL в адресную строку **внутреннего Chromium**.

Внешний noVNC всё ещё иногда долго открывается и задерживает ввод/прокрутку на 1–3 секунды. Понижение качества noVNC и разрешения экрана до 1280×720 не решило проблему. Измерения во время активной прокрутки: CPU 1,2%, throttling 0 с, чтение диска 0 МБ за 15 с; ping с Windows — 0% потерь, 145–189 мс, среднее 163 мс. Ранее Docker показал 771 МБ из лимита 1 ГБ и 147 ГБ **накопленного** block I/O; текущий замер 0 МБ/15 с не подтверждает активную дисковую нагрузку. В локальном сравнении старый и альтернативный VNC-серверы отвечали примерно за 16 мс каждый, поэтому альтернативу не развёртывали. Первый замер сетевого трафика `0,0 МБ/15 с` мог быть сделан на однострочной странице IP без видимой прокрутки и не является выводом о пропускной способности сети. Причина внешней задержки окончательно не локализована; владелец решил пока оставить noVNC как есть.

Для обычного просмотра сайтов используйте локальный браузер с совместимым клиентом VLESS + REALITY. После использования удалённого браузера остановите сеанс в панели: это освобождает память и удаляет временный профиль.

## Проверки на ПК с Windows

`bash scripts/dev.sh test` раньше требовал Linux с установленными Go и Xray, поэтому на ПК с Windows не запускался. Вдобавок при `core.autocrlf=true` Git для Windows выкладывает файлы с переводами строк CRLF, а bash в Linux-контейнере на таких скриптах падает с `$'\r': command not found`. Теперь все проверки идут в Docker (`deploy/checks`): образ собирается из содержимого будущего коммита с переводами строк репозитория, а `.gitattributes` закрепляет LF во всех checkout. При диагностике учтите, что `grep $'\r'` в Git Bash не находит CR даже в файлах с CRLF; переводы строк проверяйте через `od -c` или `rg '\r$'`.

## Подготовка переноса 8443 и Docker без Buildx — 2026-10-20

В сетях владельца 443 завершался тайм-аутом при доступном 8443, который перенаправлял на 443. Проверка с закреплённым IP также завершалась тайм-аутом, поэтому DNS не объясняет весь сбой. Точный узел или причина сбоя маршрута не установлены. На этом историческом этапе был согласован резервный вход 8443 через HAProxy. Позже владелец подтвердил Windows + Hiddify 4.1.1 + Chrome и выбрал основной вход 8443 с сохранением публикации 443; мобильная сеть требует отдельной проверки.

Перенос 8443 из Caddy в HAProxy требует сначала обновить установщик. При ошибке старый установщик может запустить прежний Caddy, пока новый HAProxy ещё держит 8443. Подготовительный релиз добавляет освобождение порта при запуске и откате, сохраняя прежнюю схему публикации.

Полный прогон также обнаружил `Unsupported architecture:` без значения: старый сборщик Docker без Buildx не заполняет `TARGETARCH`. `scripts/dev.sh` теперь получает архитектуру через `docker version` и передаёт её явным `--build-arg`.

## Гонка при открытии окна профиля в тесте — 2026-10-20

В полном Docker-прогоне тест замены подписки однажды находил её текстовое поле, но не кнопку «Новая ссылка». Поле уже появилось в DOM, а эффект `showModal()` ещё не сделал окно доступным. Тест теперь ждёт кнопку через `findByRole`, затем проверяет подтверждение и замену ссылки. Это устраняет зависимость от порядка выполнения эффекта без увеличения тайм-аутов.


## Локальный прокси выключен, а приложения продолжают обращаться к нему

На Windows после выключения Hiddify команда `curl` обращалась к `127.0.0.1:2334`
и получала отказ. Причина этой конкретной ошибки — оставшиеся переменные
`HTTP_PROXY`/`HTTPS_PROXY`, заданные BAT-файлом. Это не ответ рабочего VPS и само
по себе не объясняет тайм-аут на телефоне через LTE. Системный прокси Windows,
прокси расширения браузера и переменные окружения — отдельные настройки: сервер
их не меняет.

Для прямого теста на ПК используйте Git Bash без VPN:

```bash
curl -q -4 --noproxy '*' --connect-timeout 10 --max-time 15 \
  https://rb-gateway-3708079.duckdns.org:8443/readyz
```

В Windows CMD одинарные кавычки передаются буквально, поэтому звёздочка для
`--noproxy` должна быть в двойных кавычках. Все основные команды этой документации
предназначены для bash. Чтобы вернуть приложения в прямой режим, используйте
BAT-файл выключения прокси из инструкции Windows → Hiddify, затем перезапустите
нужные приложения. Очистка переменных только в одном окне терминала не удаляет
постоянные значения для будущих окон. Проверку прямого доступа к панели выполняйте
отдельно от проверки маршрутизации через Hiddify.
