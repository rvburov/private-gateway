# Настройка VPS одной командой с компьютера

| Роль | Что получится | ОС VPS |
| --- | --- | --- |
| `bridge` — VPS-мост | Пересылка зашифрованных TCP/Vision и XHTTP-соединений на уже работающий VPN-сервер | Ubuntu 22.04, 24.04 или 26.04, amd64 |
| `node` — выходной VPN-сервер | Самостоятельный VPN-выход со своим IP; агент получает устройства от существующего сайта управления | Ubuntu 26.04, amd64 |

Обе роли готовят пользователя, SSH-доступ и `sudo` без пароля. Мост не создаёт
новые ключи REALITY: использует профиль выхода без расшифровки. Выходной сервер
получает собственные независимые ключи TCP/Vision и XHTTP. Новая центральная
панель с отдельной базой данных устанавливается по [другой инструкции](deployment.md).

## 1. Получить исходный доступ и записать данные VPS

**Действие:** в кабинете хостинга найдите публичный IPv4, SSH-порт и имя
первоначального пользователя. Если выдан `ubuntu`, вводите `ubuntu`; если
выдан `root`, вводите `root`. Для `ubuntu` или другой обычной учётной записи
должен работать `sudo`. Отдельного нового пользователя вручную создавать не надо.
В firewall хостинга сохраните разрешение SSH и откройте TCP-порты выбранной
роли: для примера моста — `443` и `8444`, выхода — `8443` и `8444`.

**Где:** браузер → кабинет хостинга → карточка нового VPS.

**Проверка:** доступны консоль хостинга и данные первоначального входа.
Мост должен быть доступен из вашей обычной сети и достигать выходного VPS.
Выходной сервер должен достигать сайта управления по HTTPS и интернет-сайтов.

**Ожидаемый результат:** известны IP, порт, реальное имя пользователя и способ
первого входа — пароль либо уже настроенный SSH-ключ. У действия нет вывода
в консоли. Входящие порты сохранены в firewall. SSH-ключ не устраняет тайм-аут
сетевого подключения.

## 2. Скачать проверенный выпуск

**Действие:** откройте [GitHub Actions → CI/CD](https://github.com/rvburov/private-gateway/actions/workflows/ci.yml),
выберите успешный запуск после добавления мастера настройки, скачайте артефакт
`private-gateway-linux-amd64` и распакуйте ZIP. Сохраните файлы в:

```text
Windows: C:/Users/<ваш пользователь>/Downloads/private-gateway-linux-amd64
macOS/Linux: $HOME/Downloads/private-gateway-linux-amd64
```

**Где:** браузер и файловый менеджер вашего компьютера. На Windows следующие
команды выполняются в **Git Bash**, на macOS/Linux — в терминале bash.
Запускать их внутри SSH-сеанса VPS не нужно.

**Проверка — на компьютере:**

```bash
artifact="$HOME/Downloads/private-gateway-linux-amd64"
for pg_file in release.tar.gz release.tar.gz.sha256 \
  install/setup-vps.sh install/prepare-vps.sh install/verify-release.py \
  install/install-bridge.sh install/install-node.sh install/setup-node.py; do
  if [ -s "$artifact/$pg_file" ]; then
    printf 'OK: %s\n' "$pg_file"
  else
    printf 'MISSING: %s\n' "$pg_file"
  fi
done
bash "$artifact/install/setup-vps.sh" --help
```

**Ожидаемый вывод:** восемь строк `OK: ...`, затем справка с ролями
`bridge` и `node`. При `MISSING` найдите правильно распакованный артефакт;
старый выпуск без новых скриптов не подходит.

## 3. Указать данные и проверить комплект

**Действие:** замените три значения своими. Пример ниже использует исходного
пользователя `ubuntu`, а для постоянного доступа создаст `pgadmin`. Можно
указать уже существующего обычного пользователя вместо `pgadmin`.

**Где:** локальный Git Bash/терминал; команды до конца установки выполняются
в одном окне.

```bash
vps_ip='IP_НОВОГО_VPS'
vps_ssh_port='22'
vps_initial_user='ubuntu'
vps_user='pgadmin'
artifact="$HOME/Downloads/private-gateway-linux-amd64"
printf 'VPS=%s PORT=%s INITIAL_USER=%s USER=%s\n' \
  "$vps_ip" "$vps_ssh_port" "$vps_initial_user" "$vps_user"
```

**Проверка:** сравните напечатанные данные с кабинетом хостинга. Далее выберите
только одну ветку: **шаги 4–6 для моста** либо **шаги 7–10 для выходного VPN**.

**Ожидаемый вывод:** ваш настоящий IP, порт и два имени пользователя;
`IP_НОВОГО_VPS` в строке не осталось.

## 4. Мост: скачать настройку из сайта

**Действие:** в панели откройте **Серверы → карточка выходного VPS**:

| Поле | Что указать |
| --- | --- |
| Способ подключения | `Через VPS-мост` |
| Адрес VPS-моста | Публичный IP нового моста |
| Порт TCP/Vision на мосту | `443` |
| Порт XHTTP на мосту | `8444`, если XHTTP включён у выхода |

Нажмите **Сохранить способ подключения**, затем **Скачать настройку моста**.
Сохраните файл с выданным именем в `Downloads`. Адрес и порты самого выхода
не заменяйте адресом моста.

**Где:** браузер → существующая панель Private Gateway. Если прямой доступ
к панели ограничен, для получения файлов можно временно использовать рабочий VPN.

**Проверка:** в карточке показан сохранённый маршрут; в `Downloads` появился
непустой `bridge-<идентификатор>.json`.

**Ожидаемый результат:** кнопка скачивания доступна и файл получен. Сохранение
на сайте ещё не запускает мост. Новые ссылки уже указывают на мост: до завершения
установки они могут не работать. Для нескольких выходов используйте разные
входные порты; один скачанный файл объединяет выходы с тем же адресом моста.

## 5. Мост: запустить мастер

**Действие:** скопируйте точное имя скачанного JSON в переменную и выполните:

**Где:** локальный Git Bash/терминал. Не в SSH-окне VPS.

```bash
vps_bridge_config="$HOME/Downloads/bridge-ИДЕНТИФИКАТОР.json"
bash "$artifact/install/setup-vps.sh" --role bridge \
  --host "$vps_ip" --port "$vps_ssh_port" \
  --initial-user "$vps_initial_user" --user "$vps_user" \
  --artifact "$artifact" --config "$vps_bridge_config" --check
```

**Проверка:** предварительная команда проверяет локальные файлы без SSH,
создания ключа или изменений VPS.

**Ожидаемый вывод:** `LOCAL_SETUP_CHECK_OK`. Затем запустите установку:

```bash
bash "$artifact/install/setup-vps.sh" --role bridge \
  --host "$vps_ip" --port "$vps_ssh_port" \
  --initial-user "$vps_initial_user" --user "$vps_user" \
  --artifact "$artifact" --config "$vps_bridge_config"
```

Сверьте показанный SSH-отпечаток с консолью хостинга. При первом доступе могут
запрашиваться пароль исходного пользователя и пароль `sudo`. В терминале
ввод пароля не отображается; введите его и нажмите Enter. Это разные запросы
аутентификации, поэтому первоначальный пароль может потребоваться несколько раз.
После подготовки используется отдельный ключ без парольной фразы.

Если хостинг уже выдал вам SSH-ключ, в запрос **«Путь уже имеющегося ключа
хостинга»** укажите его полный локальный путь. Для обычного парольного входа
нажмите Enter. Этот ключ используется только для первоначального доступа,
не изменяется и не копируется на VPS. Его можно передать заранее отдельным
параметром `--initial-key "$HOME/.ssh/ИМЯ_КЛЮЧА_ХОСТИНГА"`; параметр `--key`
задаёт другой ключ — постоянный ключ автоматизации.
Если старый ключ хостинга зашифрован, SSH может запросить именно его парольную
фразу. Мастер её не снимает: без парольной фразы создаётся только новый
отдельный ключ автоматизации.

**Ожидаемый вывод установки:** `SSH_KEY_OK`, `SUDO_PASSWORDLESS_OK`, затем
`SETUP_DONE role=bridge`. При ошибке мастер завершится ненулевым кодом с
указанием этапа; не считайте одну успешную TCP-пробу успехом VPN.

## 6. Мост: проверить подключение клиента

**Действие:** на сайте откройте **Устройства → нужное устройство → Профиль**.
Получите обычную ссылку **VLESS · XHTTP + REALITY**, импортируйте в совместимый
клиент и включите VPN всей системы/TUN. Другие VPN отключите.

**Где:** браузер, VPN-клиент и локальный Git Bash. На macOS/Linux вместо
`curl.exe` ниже используйте `curl`.

**Проверка:**

```bash
curl.exe -q -4 --proxy '' --noproxy '*' --connect-timeout 5 --max-time 15 \
  --fail --silent --show-error --write-out '\nHTTP=%{http_code}\n' \
  https://api.ipify.org/
printf 'CURL_EXIT=%s\n' "$?"
```

**Ожидаемый вывод:** публичный IP **выходного** VPN-сервера, `HTTP=200` и
`CURL_EXIT=0`. Затем отключите XHTTP, импортируйте отдельную ссылку
**VLESS · TCP + REALITY + Vision**, подключите её и повторите команду.
Мост не переключает транспорт автоматически; оба профиля проверяются отдельно.
Если только TCP не работает в Private Gateway, используйте
[порядок сравнительной проверки](bridge.md#tcpvision-не-работает-на-windows-при-рабочем-xhttp).

## 7. Выходной VPN: запустить мастер

**Действие:** на новом чистом Ubuntu 26.04 запустите роль `node`:

**Где:** локальный Git Bash/терминал. Используются переменные шага 3.

```bash
bash "$artifact/install/setup-vps.sh" --role node \
  --host "$vps_ip" --port "$vps_ssh_port" \
  --initial-user "$vps_initial_user" --user "$vps_user" \
  --artifact "$artifact"
```

Мастер настроит доступ, установит зависимости и создаст две пары ключей
REALITY на VPS. При первом входе сверьте SSH-отпечаток и при необходимости
введите исходный пароль/пароль `sudo`, как в шаге 5. Закрытые ключи не нужно
копировать на компьютер или вставлять в чат.

**Проверка:** мастер показал открытые параметры TCP/Vision и XHTTP и ждёт
заполнения карточки сайта. Не закрывайте терминал и не запускайте второй мастер.

**Ожидаемый вывод:** строки `NODE_HOST`, `TCP_PORT`, `SERVER_NAME`,
`TCP_PUBLIC_KEY`, `TCP_SHORT_ID`, `XHTTP_PORT`, `XHTTP_PUBLIC_KEY`,
`XHTTP_SHORT_ID`, `XHTTP_PATH` и `NODE_PARAMETERS_READY`.
Это открытые данные для следующего шага. Вывод не означает, что VPN уже запущен.

## 8. Выходной VPN: добавить карточку на сайте

**Действие:** откройте **Серверы → Добавить VPS** и перенесите открытые данные,
показанные мастером:

| Поле сайта | Значение |
| --- | --- |
| Название | Ваше название нового выхода |
| Адрес VPS | Новый публичный IP из шага 3 |
| Порт TCP/Vision | Показанный мастером порт TCP, обычно `8443` |
| Server name REALITY | Показанное мастером имя |
| Открытый ключ REALITY | Открытый ключ TCP |
| Short ID | Short ID TCP |
| Дополнительные транспорты VPS | Включить `XHTTP + REALITY (HTTP/2)` |
| Порт XHTTP | Показанный мастером порт XHTTP, обычно `8444` |
| Открытый ключ XHTTP | Отдельный открытый ключ XHTTP |
| Short ID XHTTP | Short ID XHTTP |
| Путь XHTTP | Показанный путь с начальным `/` |

**XHTTP + TLS (HTTP/3, UDP)** оставьте выключенным. Нажмите **Сохранить VPS**.

**Где:** браузер → существующий сайт управления Private Gateway.

**Проверка:** открылось окно **Подключить агент VPS** с **Идентификатором VPS**
и **Кодом подключения**. Вернитесь в мастер: сначала укажите идентификатор VPS
в запросе **«UUID добавленного узла из панели»**, затем точный HTTPS-адрес
панели без `/` на конце. Код вставьте только в скрытый запрос регистрации,
когда он появится.

**Ожидаемый результат:** агент зарегистрирован; после запуска на сайте
появляется свежая связь с этим VPS. Одноразовый код действует 15 минут;
истёкший получите через **Переподключить агент**. Не передавайте код
аргументом команды, не сохраняйте его в журнале.

## 9. Выходной VPN: применить конфигурацию

**Действие:** на сайте откройте **Серверы → карточка нового VPS → Применить**.
Первая команда завершилась после регистрации агента; теперь запустите тот же
мастер с `--resume`:

**Где:** сайт — в браузере; команда — в исходном локальном Git Bash/терминале.

```bash
bash "$artifact/install/setup-vps.sh" --role node \
  --host "$vps_ip" --port "$vps_ssh_port" \
  --initial-user "$vps_initial_user" --user "$vps_user" \
  --artifact "$artifact" --resume
```

**Проверка:** на сайте применённая и нужная ревизии совпадают и больше нуля,
связь агента свежая, сообщения об ошибке нет. Мастер использует сохранённые
ключи, настройки и токен; не создавайте новую карточку для повторного запуска.

**Ожидаемый вывод мастера:** `SSH_KEY_OK`, `SUDO_PASSWORDLESS_OK`,
`SETUP_DONE role=node`. Это проверка служб; настоящий VPN-трафик проверяется
следующим шагом.

## 10. Выходной VPN: выдать профили и проверить трафик

**Действие — на сайте:**

1. **Серверы → новый VPS:** способ подключения **Напрямую к VPS**.
2. **Устройства → Добавить устройство:** выберите новый сервер подключения.
3. **Серверы → карточка нового VPS → Применить**; дождитесь равных ревизий.
4. **Устройства → созданное устройство → Профиль:** получите TCP/Vision.
5. Импортируйте профиль в клиент, отключите другие VPN и подключите его
   в режиме VPN всей системы/TUN.

**Где:** сайт и VPN-клиент на компьютере/телефоне.

**Проверка:** выполните команду шага 6 на компьютере, затем отдельно проверьте
XHTTP по собственной ссылке. С телефона откройте внешний сервис проверки IP.

**Ожидаемый результат:** оба профиля дают публичный IP нового выходного VPS;
на компьютере `HTTP=200`, `CURL_EXIT=0`. Для входа через мост назначьте его
в карточке этого выхода и выполните шаги 4–6 на отдельном входном VPS.

## 11. Проверить доступ без пароля и сохранить сведения

**Действие:** повторный SSH-доступ и административные команды используйте
с отдельным ключом мастера. По умолчанию его путь:

```text
$HOME/.ssh/private_gateway_bridge_<IP_моста>_ed25519
$HOME/.ssh/private_gateway_node_<IP_выхода>_ed25519
```

**Где:** локальный Git Bash/терминал. Для `vps_role` выберите установленную роль.

**Проверка:**

```bash
vps_role='bridge'
vps_key="$HOME/.ssh/private_gateway_${vps_role}_${vps_ip}_ed25519"
ssh -o BatchMode=yes -o IdentitiesOnly=yes -i "$vps_key" \
  -p "$vps_ssh_port" "$vps_user@$vps_ip" \
  'printf "SSH_USER=%s\n" "$(id -un)"; sudo -n id -u'
printf 'ACCESS_CHECK_EXIT=%s\n' "$?"
```

**Ожидаемый вывод:**

```text
SSH_USER=pgadmin
0
ACCESS_CHECK_EXIT=0
```

Если выбрали другое имя, первая строка содержит его. Запроса пароля и парольной
фразы нет. Ключ без парольной фразы предоставляет этому пользователю полный
административный доступ через `sudo`; храните его как секрет и не присылайте
закрытую половину в чат. Существующие ключи мастер не перезаписывает.

## Что мастер сохраняет и что проверить отдельно

- Локальный отдельный SSH-ключ на каждую роль/адрес. При явном `--key FILE`
  используется указанный путь; существующий файл не заменяется новым ключом.
- Публичный ключ в `~пользователь/.ssh/authorized_keys` VPS с сохранением
  предыдущих ключей; парольный SSH и настройки `sshd` не отключаются.
- Правило `root:root 0440` в
  `/etc/sudoers.d/private-gateway-admin-ИМЯ_ПОЛЬЗОВАТЕЛЯ`, проверенное `visudo`.
- Docker и Compose, если они отсутствовали; существующая установка не
  обновляется автоматически. На мосту состояние — `/etc/private-gateway-bridge/`,
  на выходном узле — `/etc/private-gateway-node/` и `/var/lib/private-gateway-node/`.
- Подготовительные ключи и параметры нового выхода — в закрытом
  `/etc/private-gateway-node-setup/parameters.json`; файл настроек для первой
  установки — `/etc/private-gateway-node-setup/node.env`. Они принадлежат root
  и имеют режим `0600`; при повторной подготовке ключи сохраняются.
- Журнал запуска на компьютере —
  `$HOME/.private-gateway/setup/<время>-<роль>-<адрес>.<суффикс>/setup.log`.
  Точный путь печатается как `SETUP_LOG=...`. При ошибке пришлите этот журнал
  и текст ошибки; ключи, JSON/ENV с секретами, код регистрации и VLESS-ссылки
  не присылайте.

Firewall хостинга и VPS мастер не сбрасывает и не изменяет. В кабинете хостинга
разрешите SSH и входные TCP-порты выбранной роли: для примеров моста — 443/8444,
выхода — 8443/8444. При действующем firewall VPS учтите публикацию портов Docker:
разрешение UFW само по себе не определяет весь путь пакетов контейнера.

Повторный запуск использует существующего пользователя и ключ. `node --resume`
проверяет сохранённую установку того же выпуска после применения в панели;
это не команда обновления на другой выпуск. Для ручного разбора сохранены
[SSH-доступ](ssh-access.md), [существующий SSH-пользователь](ssh-existing-user.md),
[мост](bridge.md), [выходной VPS](node-setup.md) и [история ошибок](troubleshooting.md).

## Что уже проверено при разработке

Первоначальный доступ проверен настоящими OpenSSH и `sudo` в отдельном
одноразовом контейнере Ubuntu 26.04. Тест начинает под обычным пользователем
с разрешённым `sudo`, создаёт административную учётную запись, затем повторяет
подготовку под root. Сохраняются ранее добавленный посторонний SSH-ключ и
посторонний файл sudoers; повторный запуск не дублирует новый публичный ключ.
Проверяются права `0600` для `authorized_keys`, `0440` для sudoers и отказ
некорректного ключа до создания пользователя. Далее отдельный `sshd` только
на петле контейнера принимает настоящий вход по ключу при выключенных парольном
и интерактивном способах; внутри этого SSH-сеанса выполняется `sudo -n id -u`.

**Повторить проверку — на машине разработки с Docker:**

```bash
bash scripts/test-vps-access.sh
```

**Ожидаемый вывод в конце:**

```text
REAL_SSH_SUDO_OK
VPS_ACCESS_INTEGRATION_OK
```

Порты тестового SSH наружу не публикуются, учётные записи рабочей машины и VPS
не меняются. Этот прогон действительно завершился указанными строками
