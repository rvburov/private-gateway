# Roadmap и чеклист проверок

Здесь разделены **проверенная работа**, **локальные проверки** и **то, что ещё нужно проверить на устройствах**. Исправленные ошибки с причинами находятся в [истории диагностики](troubleshooting.md), полный список клиентов — в [матрице совместимости](clients.md). Отметка `[x]` относится только к указанному серверу, устройству и способу проверки; она не подтверждает работу всех приложений из матрицы.

## Проверено на рабочем VPS и реальных устройствах

- [x] Первая установка Docker Compose на VPS `162.35.172.6` прошла через GitHub Actions: `verify` и `Deploy Docker to VPS` были зелёными. Панель открылась по `https://rb-gateway-3708079.duckdns.org:8443/`. **Это подтверждение первого рабочего релиза, а не статуса каждого последующего коммита.**
- [x] После ротации административного токена пользователь вошёл в панель; API и PostgreSQL показали подключение, Xray — актуальную применённую конфигурацию. Новый токен не помещён в Git.
- [x] На VPS обычный `vpn-smoke.py` после смены REALITY target на `www.cloudflare.com` передал настоящий VLESS-трафик и вернул `VLESS traffic OK: TLSv1.3`. Это серверная проверка, а не проверка стороннего приложения.
- [x] На iPhone профиль импортирован через QR в **Hiddify**. После повторного включения туннеля он подключился по LTE; `ipleak.net` показал внешний IPv4 шлюза `162.35.172.6`. На показанных результатах DNS были серверы Google, WebRTC — IPv4 шлюза и локальный mDNS, IPv6-тест завершился тайм-аутом. Это наблюдение одной сети, а не гарантия отсутствия утечек во всех режимах.
- [x] С ПК на Windows до смены REALITY target был доступен TCP-порт 443 (`Test-NetConnection`), а запрос через REALITY fallback к `www.microsoft.com` однажды вернул HTTP `200`. Тогда же Hiddify на Windows показывал тайм-аут. Эти сетевые пробы **не подтверждают работу VPN на ПК**; после смены target Windows-клиент не перепроверен.
- [x] Удалённый Chromium через noVNC действительно открыл сайты и показал IPv4 VPS на `2ip.io` и `api.ipify.org`. При этом загрузка иногда занимала до 10 минут, а ввод и прокрутка задерживались примерно на 1–3 секунды; скорость не исправлена.

## Проверено только в локальной среде разработки

- [x] Тесты Go, PostgreSQL, настоящего Xray, панели и сборки прошли для экспорта универсального VLESS URI. Тесты не запускают все мобильные и настольные приложения.
- [x] Созданные проектом **sing-box JSON** и **Mihomo YAML** приняты соответствующими ядрами. Оба клиента в локальном тесте передали HTTP через VLESS + REALITY к Xray и получили `200`. Это не подтверждает импорт файла оболочками Clash, Stash или приложениями на телефоне.
- [ ] Для последнего коммита `master` подтвердить на GitHub зелёные **оба** этапа `verify` и `Deploy Docker to VPS`, затем открыть панель и увидеть в профиле выбор **VLESS URI / sing-box JSON / Mihomo YAML**. Из облачной среды статус Actions и текущую версию VPS проверить не удалось.

## Что проверить владельцу на своих устройствах

### Новый вход администратора

- [ ] После зелёного CI/CD на VPS запустить `sudo python3 /opt/private-gateway-docker/current/docker/admin-credentials.py` и задать новый пароль независимо от состояния прежней учётной записи. Команда уберёт старые поля администратора из рабочего env-файла; QR и ручной ключ для **нового** аутентификатора покажет панель. Проверить, что прежний код из секрета 2FA, опубликованного в переписке, больше не действует. Секреты не присылать в чат.
- [ ] На реальном VPS проверить, что до настройки учётной записи страница показывает логин и пароль с подсказкой SSH, а не поле токена. Затем проверить вход: логин и пароль → QR/ключ 2FA в браузере → подтверждение кода → новый вход с очередным кодом без повторного QR. Проверить отказ при неверном пароле, неверном или повторном коде, выход и повторный вход. Убедиться, что устройства и применённая конфигурация Xray сохранились. Прежний токен не должен открывать API **извне** даже до настройки, а внутренний `gatewayctl status` должен работать.

### Подключения устройств

Для **каждого нового устройства** создайте отдельный профиль в панели, нажмите «Применить конфигурацию» и убедитесь, что версии совпали. Импортируйте профиль в клиент, поддерживающий VLESS + REALITY + Vision. В списке ниже отмечайте результат отдельно для каждого фактически используемого типа устройства; там, где проверка не нужна или устройства нет, пишите «не применяется».

- [ ] **ПК и ноутбук с Windows:** в актуальном v2rayN (затем, если нужен, NekoRay) импортировать VLESS URI из буфера, подключиться и открыть `https://api.ipify.org/`. Ожидаемый IPv4 — `162.35.172.6`. Предыдущий тайм-аут Hiddify на Windows после исправления REALITY не перепроверен.
- [ ] **ПК и ноутбук с macOS:** в установленном клиенте с VLESS + REALITY + Vision импортировать URI или конфигурацию sing-box, подключиться и проверить внешний IPv4. Успех на Windows не заменяет эту проверку.
- [ ] **ПК и ноутбук с Linux:** импортировать sing-box JSON либо Mihomo YAML, проверить соединение из браузера через локальный proxy и, если нужен весь трафик устройства, отдельно проверить TUN-режим. Локальный тест ядра не подтверждает эту установку.
- [ ] **Телефон и планшет с Android:** импортировать URI или QR в актуальный v2rayNG, затем при необходимости в NekoBox; проверить IPv4 на Wi-Fi и мобильной сети там, где они доступны. Android ещё не проверялся физически.
- [ ] **iPhone и iPad:** результат iPhone + Hiddify по LTE отмечен выше. Отдельно проверить Hiddify на Wi-Fi и iPad, если он есть, и импорт URI в нужные альтернативные клиенты, например Streisand или Shadowrocket. Успех одного приложения и сети не подтверждает другие.
- [ ] **Другие используемые устройства и ОС:** выбрать доступный для них клиент/ядро с VLESS + REALITY + Vision, импортировать URI или файл из панели и проверить реальный трафик. Для отсутствующего у владельца типа устройства пометить «не применяется», а не `[x]`. Для каждого планируемого клиента записать результат в [матрице](clients.md).
- [ ] Если нужны **sing-box, Clash Nyanpasu, Mihomo Party, Clash Verge или Clash Meta for Android**, импортировать JSON/YAML из панели в конкретное приложение и проверить внешний IP. Локальная проверка ядер уже прошла, но импорт и маршрутизация каждой оболочки ещё не проверены. Обычный Clash for Android без ядра Mihomo не считать совместимым.
- [ ] Для **Happ, FoXray, Karing, V2Box, Loon и Stash** сначала записать версию приложения и проверить наличие одновременно VLESS, REALITY и Vision, затем попробовать URI либо подходящий формат файла. **Quantumult X и Surge** не считать поддержанными, пока для конкретной версии не подтверждён весь протокол. Не отправлять URI, QR и файлы профиля в чат.
- [ ] В каждом успешно подключённом клиенте отдельно проверить [DNS, IPv6, WebRTC и режим маршрутизации](privacy-checks.md). Если нужен полный VPN, включить TUN/VPN-режим и проверить приложения вне браузера; импорт узла сам по себе не создаёт системный туннель. Проверить kill switch при разрыве соединения и отзыв **отдельного тестового устройства** после применения конфигурации.
- [ ] Зафиксировать для каждого испытания: **клиент и версия → устройство и сеть → URI/QR/файл → подключился ли → внешний IP → результат DNS/IPv6/WebRTC → текст ошибки без секретов**. После этого заменить в [матрице клиентов](clients.md) формулировку «внешний тест ещё нужен» на фактический результат.

## Ближайшие задачи

| Приоритет | Задача | Критерий готовности |
| --- | --- | --- |
| Высокий | Внешние зашифрованные резервные копии и пробное восстановление | Вместе сохраняются PostgreSQL, `stack.env`, конфигурация Xray и необходимые данные Caddy; копия хранится вне VPS, восстановление проверено на отдельной машине, известны срок хранения и свободное место. Нынешние локальные backups установщика не заменяют эту проверку. |
| Высокий | Перевыпустить раскрытый DuckDNS token | В кабинете DuckDNS создан новый token, старый отозван, DNS A-запись по-прежнему указывает на `162.35.172.6`. При нынешнем статическом IP нет необходимости хранить этот token в Docker-стеке. |
| После backup | Убрать остатки прежней host/Podman установки | Составлен список старых служб, каталогов, образов и учётных записей; сделана проверенная копия и пробное восстановление; затем удалены только подтверждённо ненужные компоненты. Рабочий Docker-стек, SSH-доступ и его backups сохранены. |
| Средний | Подтвердить [матрицу клиентов](clients.md) на устройствах и поведение маршрутов | Для каждого заявленного совместимого приложения записаны версия, способ импорта URI/файла и результат подключения к VPS; для неподдерживаемых явно указан предел. На Windows отдельно проверены DNS, IPv6, WebRTC, отключение туннеля и kill switch в [проверках приватности](privacy-checks.md). Форматы sing-box и Mihomo уже прошли локальный тест ядра, но не внешний тест на устройстве. |
| Средний | Наблюдение за production и восстановлением | Есть уведомления о состоянии Docker-контейнеров, истечении TLS-сертификата, заполнении диска и давности последней успешной резервной копии; сбой обновления и откат проверены в отдельной тестовой среде. |
| Средний | Дополнительные функции входа из AI Capper | После проверки базового потока отдельно решить, нужны ли резервные коды 2FA и доверенные устройства. Сейчас восстановление доступа выполняет владелец через SSH-команду со сменой пароля и новым подключением аутентификатора; «запомнить устройство» и резервные коды не показываются в панели шлюза. |

## Улучшения после стабилизации

- Проверить весь выпуск профиля из **production Docker-стека** в автоматическом сквозном тесте: созданный API профиль должен пройти настоящий VLESS-запрос через опубликованный Xray-порт. Нынешние тесты Go/Xray, серверный `vpn-smoke.py` и локальная проверка sing-box/Mihomo покрывают части этого пути, но CI не заменяет проверку внешнего клиента.
- Разделить внутренний CLI-токен и пароль Basic Auth браузера; настроить независимую ротацию и аудит доступа.
- Усилить изоляцию удалённого Chromium: проверить его сетевой доступ к API и локальной сети; для более сильной границы вынести браузер в отдельную VM. Контейнер уже работает без root и без Docker socket, но находится в сети управления browser worker.
- Обновлять Docker-образы предсказуемо: закрепить используемые образы digest, регулярно проверять обновления и уязвимости, прогонять smoke tests перед выпуском.
- После стабилизации одного VPS рассмотреть несколько узлов Xray, роли пользователей и расширенный административный аудит.

## Отложено по решению владельца

Удалённый браузер через noVNC остаётся медленным при вводе и прокрутке. Снижение качества и разрешения не помогло; активной нагрузки CPU и диска замеры не показали. Причина внешней задержки не установлена. Владелец решил оставить текущий браузер без дальнейшей переделки. Если потребность в плавной удалённой графической сессии появится снова, начать с повторяемого замера на длинной странице через другую сеть/клиент и только затем выбирать другое средство передачи изображения или расположение VPS. Увеличение CPU без новых данных не является подтверждённым решением.
