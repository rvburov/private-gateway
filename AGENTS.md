# Правила работы с Private Gateway

Этот файл автоматически читают агенты разработки. Имя `AGENTS.md` используется по соглашению инструментов и сохраняет совместимость с checkout на Windows.

## Проект и инварианты

- Рабочий production — Docker Compose на Ubuntu 26.04 amd64: PostgreSQL 18, Go API, Xray, временный Chromium/noVNC и Caddy. Не возвращайте host systemd/Podman как основной способ запуска.
- Используйте Go, `pgx/v5`, PostgreSQL 18 и SQL-запросы `sqlc`. SQLite не добавлять. После изменений SQL запускайте `sqlc` 1.30.0; файлы `internal/storage/db` вручную не редактировать.
- Xray должен передавать трафик независимо от доступности PostgreSQL. Изменение конфигурации выполняется после проверки настоящим Xray; при ошибке запуска возвращается предыдущий рабочий конфиг.
- Сохраняйте различие между желаемой и применённой ревизиями. Создание и отзыв устройства требуют успешного применения к работающему Xray. Один ответ порта 443 или `/readyz` не доказывает, что VLESS-профиль работает.
- Панель и noVNC доступны через HTTPS Caddy на 8443; Xray принимает VLESS + REALITY на 443. Внутренние API, PostgreSQL, browser worker и VNC наружу не публиковать.
- Production-браузер держать в отдельном Docker-контейнере с непривилегированным UID, без Docker socket, host mounts и шлюзовых секретов. Его профиль временный; текущую задержку noVNC не описывать как исправленную.

## Секреты и данные

- Токены, пароли, закрытые SSH/REALITY-ключи, VLESS URI и QR-коды не хранить в Git, документации, аудит-журнале, URL веб-запросов или аргументах процессов. Не просить прислать их в чат. Профиль выдавать только отдельной авторизованной операцией.
- Публичная страница входа не должна раскрывать внутренние команды VPS или состояние первоначальной настройки администратора. Эксплуатационные команды держите в закрытом рабочем процессе и документации для владельца.
- Публичный API принимает только временный сеанс, выданный после проверки логина, пароля и TOTP; до настройки учётной записи публичного входа нет. Логин и хеш пароля хранятся в PostgreSQL; TOTP подключается и подтверждается в браузере, после чего его секрет хранится в базе зашифрованным. Секрет не печатать в терминале. Долгоживущий `GATEWAY_API_TOKEN` оставлен только для локального CLI внутри API-контейнера. Caddy допускает к noVNC только по отдельному короткоживущему cookie, связанному с подтверждённым сеансом администратора; без второго фактора обхода быть не должно. Смена логина и пароля выполняется только root-командой на VPS с backup и откатом и требует нового подключения 2FA в браузере.
- GitHub Secrets содержат только SSH-доступ для CD. Секреты приложения находятся на VPS в `/etc/private-gateway-docker/stack.env`; локальный `.env` на ПК GitHub Actions не читает. При раскрытии действующего секрета ротировать его и проверить доступ без вывода нового значения.
- Для backup нужны согласованные копии базы **и** ключей из env. Не удалять старую установку и backups до проверенного восстановления.

## Разработка, проверка и выпуск

- Автор и коммитер всех новых коммитов: `Roman Burov <romanburov89@gmail.com>`. Не добавлять соавторов или подписи других авторов.
- Используйте существующий checkout: облачная задача уже изолирована, отдельный worktree без явного запроса не создавать. Сохраняйте чужие незакоммиченные изменения.
- Перед коммитом запускайте `bash scripts/dev.sh test`. Эта команда должна реально выполнить PostgreSQL и Xray проверки; пропущенные интеграционные тесты отмечайте как пропущенные, а не успешные. Для релизных/деплойных изменений выполняйте связанные проверки скриптов и Docker-конфигурации.
- Каждый успешный push в `master` запускает CI и затем автоматический CD на VPS. Не отправляйте в `master` экспериментальные или частично проверенные изменения; после push различайте зелёный `verify`, зелёный `Deploy Docker to VPS` и фактическую проверку сервиса. Если доступ к Actions недоступен, прямо отмечайте, что статус не подтверждён.
- Не меняйте производственный VPS, firewall, SSH и службы вручную вне задачи по эксплуатации/развёртыванию. При авторизованном развёртывании пользуйтесь проверенным релизом, сохраняйте TLS-проверку, подписи пакетов и контрольные суммы. Не отключайте проверки ради успешного запуска.
- Ошибка при обновлении требует проверки backup и текущего состояния перед повтором. Рабочую базу не удалять через `docker compose down --volumes` при обычной остановке.

## Документация и сообщения

- После существенного изменения синхронизируйте `README.md`, `docs/deployment.md`, `docs/browser.md` и проверки приватности по затронутой теме. Исправленные случаи записывайте в `docs/troubleshooting.md`; в `docs/roadmap.md` ведите отдельные чеклисты подтверждённых проверок и незавершённых задач, не приравнивая локальный тест к работе на устройстве.
- Разделяйте подтверждённые результаты CI, серверного smoke test и проверки реального клиента. Сейчас подтверждён iPhone Hiddify по LTE; новый профиль Windows, kill switch и скорость noVNC не объявлять проверенными или исправленными.
- Профиль и интерфейс не привязывать к Hiddify: основным переносимым форматом остаётся стандартный VLESS URI/QR для клиентов с REALITY и Vision. sing-box/Mihomo получают собственные конфигурации; для клиентов без VLESS + REALITY совместимость не обещать.
- В пользовательских инструкциях явно указывайте, где выполняется команда: Windows PowerShell, SSH на VPS или локальный checkout. Давайте короткие проверяемые шаги и ожидаемый результат без показа секретов.
