# Roadmap и журнал проблем развёртывания

Этот файл фиксирует проверенные факты и открытые задачи. Зелёный CI и работающая веб-панель не доказывают, что Hiddify подключается. Docker-переход меняет способ запуска и диагностики, но сам по себе не исправляет непроверенную совместимость клиентского профиля.

## Что уже произошло

| Случай | Причина или подтверждённый результат | Состояние |
| --- | --- | --- |
| Доступ к VPS из облачной среды срывался, хотя SSH был открыт на `0.0.0.0:22` | На самом VPS пользователь `romanburov` подтвердил Ubuntu 26.04 amd64, SSH-порт 22, 3.3 ГиБ RAM и около 69 ГиБ свободного места. Доступ с его Windows и из облака имел разные сетевые условия. | Установка выполняется через терминал пользователя; серверные ключи не передаются в чат. |
| `ssh` с Windows запросил пароль и остался без вывода | Для `ssh -N -L ...` это ожидаемо: туннель работает, пока окно PowerShell открыто. Первый `Connection reset` был отдельной сетевой ошибкой. | Разъяснено; панель через туннель открывалась. |
| На Windows было несколько папок релиза, одна не содержала исправленный `--resume` | Команда `scp` сперва указала несуществующий путь, а старые файлы легко было смешать с новыми. | Новый установщик проверяет, что сам скрипт и verifier взяты из того же архива. |
| Первый Docker bootstrap получил `404` при загрузке скрипта с `raw.githubusercontent.com` на VPS | Закрытый репозиторий не предоставляет анонимный доступ к исходникам; проверка checksum не смогла прочесть скачанный файл. | CI/CD выдаёт отдельный маленький артефакт `private-gateway-bootstrap` с checksum и SHA коммита. Его передают по `scp` один раз; полный релиз после этого доставляется Actions без ПК. |
| Первая Docker-установка завершилась при запуске браузера: `range of CPUs is from 0.01 to 1.00` | Compose запрашивал лимит 2 CPU, а на VPS Docker обнаружил 1 CPU. | Лимит браузера снижен до 0.75 CPU. Установщик удалил незавершённый Docker-стек до переключения старых служб; первый релиз нужно повторно проверить после нового коммита. |
| Следующая Docker-установка дошла до запуска HTTPS, но `/readyz` на 8443 не прошёл | Caddy завершался с `exec /usr/bin/caddy: operation not permitted`: образ требует `NET_BIND_SERVICE` для бинарника, а Compose сбрасывал все capabilities. На Windows TCP 80 был доступен. | Добавлен только `NET_BIND_SERVICE` при сохранении остальных ограничений; CI запускает Caddy с тем же профилем. При ошибке установщик выводит `curl` и журнал Caddy перед откатом. |
| Первый успешный Docker Deploy показал список `assets/` и `index.html` вместо панели | Файлы веб-сборки имели права `0600` и принадлежали `root`; API с UID 10001 видел каталог, но не мог прочитать `index.html`. `/readyz` не проверял содержимое панели. | Образ API назначает владельцем веб-файлов UID 10001; CI проверяет чтение страницы и assets этим пользователем, а установка и обновление требуют настоящий HTML панели. |
| Проверка `sha256sum` была набрана с разрывом имени файла | Повторная проверка `release.tar.gz.sha256` и release manifest для `4821fe3` дала OK. | Новый установщик проверяет checksum и manifest ещё раз. |
| Первая сборка браузера в Podman остановилась с `could not find pasta` | На VPS не был установлен пакет `passt`; после установки `pasta` появился. | Старая схема заменена Docker. |
| Podman отказал в `--tmpfs ... uid=10001` | Эта версия не принимает `uid` как опцию tmpfs. Позже tmpfs создавался без неё. | Старая схема заменена Docker. |
| Podman/rootless worker требовал отдельного socket, cgroups, `--resume-browser` и ручного переноса исправленных файлов | Ручной запуск был хрупким. Релиз `4821fe3` затем прошёл серверный smoke test браузера и API/Xray, но это не доказало работу Hiddify. | Новый Docker Compose и один установщик вместо прежнего production-скрипта. |
| FreeDNS `rb-gateway-3708079.mooo.com` отвечал NXDOMAIN даже с авторитетных `ns*.afraid.org` | Запись отсутствовала в опубликованной зоне, поэтому приложение не могло её исправить кодом. | Использован `rb-gateway-3708079.duckdns.org`; публичный DNS вернул `162.35.172.6`. |
| Панель на `https://rb-gateway-3708079.duckdns.org:8443/` открылась | HTTPS-запрос возвращал `200`, TLS-проверка `0`, API показывал «подключён». | Веб-доступ подтверждён в старой установке. В Docker нужен повторный тест. |
| Порт 8443 пришлось выделить отдельно от 443 | На 443 работает Xray/REALITY, а Caddy выдаёт панель по HTTPS на 8443; приложение API при этом оставалось только на loopback старого сервера. `ufw` на VPS был выключен, поэтому доступность портов зависит также от сетевых правил провайдера. | Docker сохраняет эту схему портов и не публикует внутренний API. |
| Порт 443 был доступен и `curl --resolve` к `www.microsoft.com` вернул HTTP 200 с корректным TLS | Это проверило TCP и fallback REALITY, но не авторизацию VLESS клиента. | Проверено только частично. |
| Локальный клиент Xray на VPS при настоящем VLESS-запросе получил `ConnectionResetError` | Проблема воспроизвелась без Hiddify и внешней сети телефона. Ранний smoke test не показывал, на каком этапе произошёл сброс. | **Открыто.** Добавлена сверка профиля с применённым Xray и указание этапа сбоя; по новому выводу установить причину. |
| Hiddify на Windows показал тайм-аут | По имеющимся данным нет клиентского и серверного VLESS handshake-лога для точной причины. | **Открыто.** Требуется новый профиль и end-to-end тест после Docker-установки. |
| Hiddify на iPhone не импортировал профиль, ошибка `Connection refused 127.0.0.1` | Это локальный адрес iPhone, куда клиент пытался обратиться при импорте. Это не проверка связи с VPS. | **Открыто.** Импортировать новый URI текстом/буфером и отдельно проверить подключение. |
| В панели не было QR-кода | Выдавался только текстовый VLESS URI. | Запланирован QR с локальной генерацией в браузере и предупреждением о секрете. |
| Пользователь показал скриншоты DuckDNS token и VLESS URI | Эти значения стали известны вне устройства. | **Нужно:** перевыпустить DuckDNS token в кабинете; старая чистая установка и новые ключи заменят прежние URI. Новые секреты не публиковать. |

## Приоритеты после Docker-установки

1. **Подтвердить реальный VPN-трафик.** Создать новое устройство, применить конфигурацию, импортировать новый URI на Windows и iPhone, проверить handshake и HTTP через туннель с двух сетей. Если не работает, записать только время, имя клиента и очищенные диагностические журналы, сопоставить их с Xray container log. Проверить SNI, `fp=chrome`, `flow=xtls-rprx-vision`, REALITY public key, short ID и часы устройств. Затем добавить воспроизводимый тест клиентского профиля в CI, чтобы regression обнаруживалась до VPS.
2. **Проверить публичный браузер.** Убедиться, что Basic Auth, загрузка noVNC, WebSocket/VNC, запуск/остановка и очистка tmpfs работают именно через домен и HTTPS. Серверный smoke test не заменяет эту проверку.
3. **Перевыпустить DuckDNS token.** Он был показан на скриншоте. При статическом IPv4 серверу не требуется хранить этот token. Удалить его из ненужных устройств/скриптов, а DNS A-запись оставить направленной на VPS.
4. **Сделать внешнюю зашифрованную резервную копию и пробное восстановление.** Сохранять вместе Docker volume PostgreSQL, env с ключами и необходимые файлы конфигурации. Добавить понятный скрипт backup/restore и проверку свободного места.
5. **Проверить первую установку и обновление Docker на VPS.** После одноразовой настройки SSH-приёмника CI/CD передаёт и первый релиз, и последующие обновления напрямую на сервер; скачивать большой артефакт на ПК не требуется. Нужны секреты репозитория и фактический зелёный `Deploy Docker to VPS`. Затем проверить восстановление при искусственной ошибке в отдельной тестовой среде.
6. **Удалить старый стек VPS после пунктов 1–4.** Проверить остановленные службы, архивировать старые данные, затем удалить старые systemd unit-файлы, Podman образ/пользователя, host PostgreSQL, старые каталоги в `/opt` и временные папки в home. Не удалять старый `gateway.env` и backup до проверки восстановления.

## Дальнейшие улучшения

- QR-код для URI устройства, формируемый локально в панели без передачи профиля внешнему сервису.
- Разделить доступ администратора к панели и пароль браузера; добавить ротацию токенов без переустановки.
- Увести браузер в отдельную VM, если нужна изоляция сильнее Docker; рассмотреть постоянные сессии только с отдельным шифрованием и явным сроком жизни.
- Обновления базовых Docker-образов с закреплёнными digest, проверкой уязвимостей и повторными smoke tests.
- Мониторинг срока сертификата, места на диске, состояния контейнеров и последней успешной резервной копии.
- Несколько узлов Xray, роли пользователей и аудит административного доступа после стабилизации одного VPS.
