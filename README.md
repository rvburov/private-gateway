# Private Gateway

Платформа управления личным VLESS + REALITY шлюзом и отдельным удалённым браузером. Xray передаёт трафик, Go API управляет устройствами и конфигурациями, PostgreSQL 18 хранит состояние. Людям для подключения выдаётся ссылка-подписка: приложение VPN само получает по ней профиль в своём формате и обновляет его. Доступны и стандартная VLESS-ссылка с QR-кодом, и конфигурации sing-box и Mihomo.

## Что работает в версии 0.1

- Go API с `chi`: терминал задаёт логин и пароль, браузер после проверки пароля подключает приложение-аутентификатор через QR и подтверждает шестизначный TOTP-код. После входа панель использует временный сеанс. В production API опубликован только через HTTPS Caddy.
- PostgreSQL 18, `pgx/v5`, запросы `sqlc`, встроенные миграции `golang-migrate`.
- Создание и отзыв устройств, удаление отозванных устройств после применения конфигурации, отдельный UUID каждого устройства, экспорт VLESS URI, QR-кода и конфигураций sing-box/Mihomo.
- Ссылка-подписка `https://ДОМЕН/sub/…` для каждого устройства: base64-список `vless://`, YAML Mihomo или JSON sing-box по приложению, страница с кнопками импорта для браузера. В базе хранится только хеш её секрета; «Новая ссылка» сразу заменяет прежнюю, отзыв устройства её отключает ([подробнее](docs/clients.md#ссылка-подписка)).
- AES-256-GCM для учётных данных устройств и TOTP-секрета администратора в PostgreSQL; главный ключ шифрования хранится вне базы. Пароль администратора хранится в базе только как PBKDF2-хеш.
- Проверка конфигурации настоящим Xray, атомарная запись и откат при ошибке перезапуска.
- CLI `gatewayctl` на Cobra и панель React / TypeScript / Vite / TanStack Query. На компьютере у панели боковое меню, на телефоне — нижние вкладки, круглая кнопка «Добавить» и шторка «Ещё»; тема светлая, тёмная или как в системе. В разделе «Инструкции» выберите Android, iPhone, Windows, macOS или Linux и нажмите нужный клиент: его страница ведёт от установки и импорта профиля до подключения и проверки. Для Windows → Hiddify есть проверенные настройки системного прокси и скачиваемые BAT-файлы. В разделе «Проверка» кнопка «Проверить безопасность» показывает провайдера выхода, IPv6, WebRTC, DNS и признаки отпечатка браузера; отличающийся DNS-резолвер отмечается для проверки, но сам по себе не считается доказанной утечкой. В разделе «Сервер» кнопка «Проверить сервер» проверяет службы вплоть до настоящего VLESS-запроса через Xray, измеряет скорость и HTTP-задержку до VPS и в интернет и показывает доступную нагрузку. Там же — история замеров для ручного сравнения сетей. У разделов отдельные результаты и скачиваемые отчёты; проверка безопасности не запускает тест скорости. В «Проверке» также приведены 10 сайтов для ручной проверки ([подробнее](docs/privacy-checks.md#раздел-проверка-в-панели)).
- Управление временным браузером в отдельном Docker-контейнере; noVNC через HTTPS и подтверждённый сеанс администратора после 2FA.
- Журнал действий, защищённые Prometheus metrics, HTTP instrumentation OpenTelemetry.
- CI: те же проверки в Docker, что `bash scripts/dev.sh test` на ПК, — Go с PostgreSQL 18 и настоящим Xray под `-race`, панель, скрипты выпуска и workflow; релиз собирается в том же образе. Установку, обновление и откат CI проверяет на чистом Ubuntu 26.04 настоящими скриптами сервера.
- Docker Compose установщик Ubuntu 26.04 из проверенной сборки GitHub Actions; после успешной проверки коммита в `master` релиз автоматически доставляется на все серверы из `deploy/servers`. Сервер проверяет панель и настоящий VLESS-трафик и при сбое откатывается; контейнер пересоздаётся, только если изменился его образ. Панель каждого сервера затем проверяется снаружи. Новый сервер добавляет одна команда `bash scripts/add-server.sh` ([инструкция](docs/deployment.md#новый-сервер)).
- Основной адрес production-панели — `https://rb-gateway-3708079.duckdns.org:8443/`. HAProxy обслуживает панель и VLESS + REALITY на 8443; внешний 443 сохранён для совместимости. Все новые профили и подписки используют 8443 без выбора порта. Старые недоступные подписки на 443 нужно [однократно переимпортировать](docs/clients.md#переход-с-профиля-на-443). Переход существующего сервера требует [двух отдельных выпусков](docs/deployment.md#основной-внешний-вход-8443-с-сохранением-443). В панели видны байты трафика отдельно по активным профилям с последнего запуска Xray.

Добавление или отзыв устройства **создаёт ожидающую применения ревизию**. Чтобы реально изменить доступ, выполните `config apply`. Панель показывает различие между желаемой и применённой ревизиями. Ключ отозванного устройства перестаёт работать после успешного применения. Затем отозванное устройство можно удалить из списка; журнал сохранит только его идентификатор и историю действий.

## Локальная разработка

Правила для ИИ-агентов и параллельной работы в отдельных рабочих папках — в [AGENTS.md](AGENTS.md).

### Claude Code в облаке

Claude Code может работать с репозиторием и без ПК: на [claude.ai/code](https://claude.ai/code), в приложении Claude или командой `claude --cloud`. Сессия получает свежий клон с GitHub в отдельной машине с Docker и сама читает AGENTS.md. Подготовка — один раз:

1. На claude.ai/code подключите GitHub и установите приложение Claude на репозиторий `rvburov/private-gateway` (оно закрытое, поэтому без установки сессии его не увидят).
2. В настройках облачной среды (environment) выберите доступ к сети **Custom**, оставьте стандартный список доменов и добавьте строку `deb.debian.org`: без неё не соберётся образ проверок. Переменные окружения и setup script не нужны, секреты туда не кладите.
3. Начните сессию с репозиторием `rvburov/private-gateway` и опишите задачу.

Подписи Claude в коммитах отключены в `.claude/settings.json`, а автором коммитов облачной сессии [`scripts/cloud-session.sh`](scripts/cloud-session.sh) ставит владельца. Как и Codex, облачный Claude отправляет работу только по вашей просьбе. «Отправь ветку» запускает CI без выкладки. «Отправь в master» означает, что он подтянет свежий `master`, прогонит проверки и отправит перемоткой, а затем последует выкладка на серверы. Пока работа не отправлена, она есть только в машине сессии.

**Проверки** запускаются одной командой и целиком идут в Docker. Нужен только Docker: Docker Desktop на Windows и macOS (на Windows команду вводят в Git Bash), Docker Engine в Linux.

```bash
bash scripts/dev.sh test
```

Образ [deploy/checks](deploy/checks/Dockerfile) содержит Go 1.26.9, Node.js 22, Python, настоящий Xray 26.3.27 и sqlc 1.30.0; загрузки сверяются по SHA-256. Рядом во временном контейнере без открытых портов работает PostgreSQL 18. Образ собирается из содержимого будущего коммита, поэтому `.env` и другие игнорируемые файлы в него не попадают, а переводы строк совпадают с репозиторием на любой ОС. Первый запуск скачивает около 2 ГБ образов, повторные идут быстрее. В конце выводятся числа тестов Go и каждый пропущенный тест с причиной. После изменения SQL-запросов или миграций код `internal/storage/db` обновляет `bash scripts/dev.sh sqlc`. Релиз закоммиченной версии собирает `bash scripts/dev.sh release ПАПКА` в том же образе, как и CI.

**Локальный запуск API и панели** тоже идёт в Docker, на любой ОС с Docker (на Windows — из Git Bash):

```bash
bash scripts/dev.sh start   # собрать из рабочей папки и запустить PostgreSQL, API с панелью и Xray
bash scripts/dev.sh admin   # задать логин и пароль администратора; 2FA подключается в браузере
bash scripts/dev.sh stop    # остановить, сохранив базу и состояние Xray
```

`start` собирает релиз из текущей рабочей папки вместе с незакоммиченными правками в том же образе, что и проверки, и запускает production-образы api и xray с PostgreSQL 18 по `deploy/docker/compose.yml` и дополнению `deploy/dev/compose.yml`. Панель открывается на `http://127.0.0.1:8080/`; Caddy, HAProxy и удалённый браузер локально не запускаются, Xray наружу не публикуется. При первом запуске создаётся `.local/dev/stack.env` со случайными локальными секретами (значения не выводятся); повторный `start` пересобирает образы и сохраняет данные. Production-учётные данные создаются [на VPS через терминал](docs/deployment.md#учётная-запись-администратора). Не отправляйте секреты в переписку или журналы.

`bash scripts/dev.sh smoke` проверяет работающий стек целиком: создаёт устройство, выдаёт профиль, применяет конфигурацию настоящим Xray, отзывает устройство и применяет снова. CLI `gatewayctl` работает внутри контейнера API:

```bash
bash scripts/dev.sh ctl status
bash scripts/dev.sh ctl node list
bash scripts/dev.sh ctl device add macbook --node NODE_ID
bash scripts/dev.sh ctl device list
bash scripts/dev.sh ctl config apply
bash scripts/dev.sh ctl device export DEVICE_ID
bash scripts/dev.sh ctl device revoke DEVICE_ID
bash scripts/dev.sh ctl device delete DEVICE_ID
```

Экспорт выводит действующий секретный URI. UUID устройства из `device list` — идентификатор записи, отличный от UUID доступа внутри профиля. Профиль локального стека указывает на `127.0.0.1:443` и служит для разработки, а не для подключения устройств.

`bash scripts/setup-cloud.sh` готовит облачную среду без Docker-образа проверок: ставит проверенные Go, sqlc и Xray в `/workspace/.toolchains` и скачивает зависимости Go и панели.

## Удалённый браузер

На VPS он входит в Docker Compose по [docs/browser.md](docs/browser.md). Браузер работает, но удалённая графическая сессия noVNC сейчас реагирует на ввод и прокрутку с задержкой около 1–3 секунд. Для обычного просмотра сайтов удобнее локальный браузер с совместимым VLESS + REALITY клиентом. Управление через панель или в SSH на VPS:

```bash
sudo docker exec private-gateway-api-1 /usr/local/bin/gatewayctl browser start
sudo docker exec private-gateway-api-1 /usr/local/bin/gatewayctl browser status
sudo docker exec private-gateway-api-1 /usr/local/bin/gatewayctl browser stop
```

Сессия временная: после остановки данные браузера удаляются. Контейнер не получает секретов шлюза и не монтирует каталоги хоста. noVNC доступен через HTTPS Caddy после входа в панель по логину, паролю и коду 2FA; отдельного пароля нет.

## Проверки и документация

`bash scripts/dev.sh test` выполняет тесты с настоящим PostgreSQL и Xray. Тест Xray передаёт HTTP через локальный REALITY-туннель, отзывает старый ключ и проверяет новый. Вне Docker без `TEST_DATABASE_URL` интеграционные тесты PostgreSQL пропускаются, без `PRIVATE_GATEWAY_REAL_XRAY_BINARY` — реальные проверки Xray; такой запуск не заменяет интеграционные проверки. В Docker обе переменные заданы, и пропуск такого теста проваливает прогон. Сборку production-образов и проверки Caddy и HAProxy выполняет GitHub Actions.

На Linux с установленными Go, Node.js и Xray основные проверки можно повторить и без Docker:

```bash
go test -race ./...
go vet ./...
cd web
npm ci
npm test
npm run build
```

## Порты и обновление

Caddy принимает внешний TCP 80 для HTTP-01 и перенаправляет HTTP на HTTPS с `:8443`, сохраняя путь и параметры. HAProxy владеет внешними TCP 8443 и 443 и по SNI направляет панель в `caddy:443`, а REALITY — в `xray:443`. Внешний порт профиля `GATEWAY_PORT=8443` отделён от внутреннего `GATEWAY_XRAY_PORT=443`. Наличие второго входа не означает автоматического переключения приложения.

Подготовительный выпуск обновляет определение портов релиза, smoke test и откат. После подтверждённой отдельной выкладки следующий выпуск переводит канонические ссылки и профили на 8443; порядок и проверка updater — в [развёртывании](docs/deployment.md#основной-внешний-вход-8443-с-сохранением-443). Прежний подготовительный коммит `f4c5781` относился к более раннему переносу владения 8443 между Caddy и HAProxy. Обычный Docker без Buildx по-прежнему поддерживается.
